## 外部"运营AI"与数据更新接口（v1.1.0 新增）

> **来源**：business_concept v1.1 §11
> **说明**：AI在本项目中是系统外的运营生产角色，不是用户请求链路中的实时推理角色

### 运营AI职责

运营AI是一个跑在外部的自动化脚本或智能体，工作是定期的、异步的：
1. **全网选品**：去各大平台（1688、Temu、Amazon等）搜罗商品
2. **动态定义与组合标签**：标签维度和清单不是写死在代码里，AI可灵活组合生成新的标签维度和标签项
3. **撰写Item Card与推荐文章**：为每个商品预先生成"为什么好玩"、"为什么推荐"等内容

### F-040-22 运维/数据更新接口

为让外部运营AI将工作成果推入系统，本系统必须开放**运维/数据更新接口**（API Endpoint或CLI命令）。

**设计要求**：
- **严格鉴权**：必须带有Token鉴权机制（Authorization: Bearer \<token\> 或 X-Admin-Key）
- **初始化与动态更新能力**：可插入新的"标签维度"、"标签清单"以及包含完整预生成推荐文案的"Item Card"
- **数据范围**：
  - 标签维度（dimension）与标签项（tags）增量/覆盖更新
  - Item Card内容（标题、摘要、卖点、场景、注意项）
  - 推荐解释文案（按标签组合预生成并存储）
- **契约约束**：
  - 幂等写入（同request_id重放不重复写）
  - 支持dry-run校验（仅验签/验结构，不落库）
  - 必须返回字段级错误列表

### 用户的纯数据库查询逻辑

1. 用户在前端选择感兴趣的标签，或由订阅记录生成标签矩阵
2. 系统直接拿标签矩阵，通过**纯数据库查询**进行交叉筛选
3. 对筛选结果进行**随机化打乱或抽选**，最终展现包含预生成推荐文案的结果
4. 全程**零实时AI参与**

## 底层架构设计
本项目应坚持“AI Agent原生友好”的设计原则。意味着，本项目的所有对外数据接口都应考虑AI的使用场景。包括但不限于：


### 浏览类接口
- 特定用户的推荐 item list
- 特定标签的推荐 item list
- 特定来源的推荐 item list
- 特定时间范围的推荐 item list
- 指定item的推荐 summary、direct link等信息


### 用户类接口
- 用户注册、登录、注销等
- 用户个人喜好管理、特定标签订阅、特定标签过滤、特定来源过滤等
- 用户订阅、取消订阅、查询订阅信息等


### 管理类接口（用于本系统的运营及维护Agent）
- 更新系统全局参数、配置等
- 更新特定标签的推荐 item list
- 更新特定item的推荐 summary、direct link等item card信息


因此，系统中应该有一层特定且全系统唯一的数据API层，用于封装数据底层（D1、R2等），并统一响应AI Agent的调用（代表AI agent用户，通过CLI（比如curl）、webhook等方式获取数据，并产生交互），以及web前端的调用（代表人类用户，通过浏览网页的方式获取数据，并产生交互）。有了统一的该数据API层后：
- Agent和人类这两类用户的数据呈现可实现完全的一致；
- Agent类用户又能极其方便的获取到结构化的数据，而不用去抓取网页并解析，更不用去处理复杂的页面逻辑进行交互（比如注册、付费等）。
- 保障数据安全：所有对外访问必须经API层（以及鉴权等机制），禁止前端/Agent直连D1/R2。

## 数据格式宏观设计
在数据层面，本项目同样应坚持“AI Agent原生友好”的设计原则。意味着，本项目的所有数据（除了需要快速进行多维度查询的数据），应该优先以markdown的格式进行编写及存储。包括但不限于：


### 系统全局参数和配置
- 标签一级维度清单
比如：使用场景、价格区间、商品特点、目标人群、行业归属等。
- 标签二级维度清单
比如：家庭、手工、户外、科技、教育、食物、工具、少女、少男、老人等。
- 首页推荐标签
- 用户首页推荐item（个性化）
- 用户登录失效时间

### item数据
每一个item数据都应该以一个markdown格式的item card格式存储，包括但不限于：
- item uuid
- item name
- item promote summary：
由运营的内部Agent进行持续更新的推荐理由（markdown格式）。
- item 标签：
由运营的内部Agent进行持续更新的所属标签。一个item可以有（也应该有）多个标签，才能形成多维度复合推荐。
- item price
- item direct link等。

### 数据“主从”存储
- D1 存结构化字段，尤其是item uuid、标签一级维度、标签二级维度、用户ID、用户订阅标签等，方便进行多维度标签的快速复合检索
- R2 存 markdown item card数据及必要的资产（如图片等）

注意：上述数据仅为举例，实际数据以运营中不断积累和分析的数据为准。

# 系统 Agent 协作流程说明

整个系统由 **研发 Agent 团队** 与 **运营 Agent 团队** 两部分组成，各 Agent 分工明确，通过特定的文档与文件夹流转完成闭环协作。

## 一、研发 Agent 团队

研发团队主要负责将商业概念转化为可执行的代码，并对代码质量进行把控。

| Agent 名称 | 主要职责 | 输入 (Input) | 输出 (Output) | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| **Designer** | 需求分析与架构转化 | `Business Concept` (商业概念)<br>`System Design` (系统设计) | **SRS 文档**<br>(系统需求规格说明书) | 研发流程的起点 |
| **Coder** | 代码实现与维护 | **SRS 文档、STR 文档** | 1. 应用程序代码<br>2. **API 文档** (维护) | 需响应 **STR 文档** 中的反馈进行代码修改 |
| **Reviewer** | 代码审查与反馈 | **代码**<br>**API 文档** | **STR 文档**<br>(软件测试/评审报告) | 记录发现的问题及可优化提升的部分 |

**研发流程简述：**
`Business Concept` → **Designer** → `SRS 文档` → **Coder** → `Code + API 文档` → **Reviewer** → `STR 文档` → *(反馈至)* **Coder** (循环修改至通过)。

---

## 二、运营 Agent 团队

运营团队主要负责商品的选品、内容包装以及最终的上架决策。

| Agent 名称 | 主要职责 | 操作目录/来源 | 产出/目标目录 | 具体动作说明 |
| :--- | :--- | :--- | :--- | :--- |
| **选品 Agent** | 海量初筛与发现 | 原始设定网站：<br>TEMU、1688、亚马逊等电商平台 | **`/selected`** 文件夹 | 抓取**最新、最热、最有趣、最搞怪、有热点**的商品，依据选品逻辑更新并存入备选区（每个商品一个编号及一个markdown文件）。 |
| **包装策划 Agent** | 内容二次创作 | 读取 **`/selected`** 文件夹下的商品链接 | **`/candidate`** 文件夹 | 对商品进行描述分析，策划生成**推广文案**。文案需阐述商品的有趣之处及尝试理由，用于平台前端展示。（每个商品一个编号及一个markdown文件） |
| **审核决策 Agent** | 最终质量把关与上架 | 读取 **`/candidate`** 文件夹 | **`/pass`** 文件夹 (成功)<br>**`/notpass`** 文件夹 (失败)<br>**平台数据库** | 逐个决策商品是否具备爆款潜力。<br>• **通过**：归档至 `/pass`，并依据研发团队的 **API 文档** 上架至数据库。<br>• **拒绝**：归档至 `/notpass`，不上架仅做留存。（每个商品一个编号及一个markdown文件） |

**运营流程简述：**
`电商原始数据` → **选品 Agent** → `/selected` 文件夹 → **包装策划 Agent** → `/candidate_item` 文件夹 → **审核决策 Agent** → (`/pass`归档 + `数据库上架`) 或 (`/notpass` 归档)。

---

## 三、协作闭环

- **研发输出对接运营**：研发 Coder 维护的 **API 文档** 是运营审核 Agent 执行最终商品上架、商品下架、标签维护等数据操作的技术依据和唯一接口。
- **文件夹结构**：
    ```
    project_root/
    ├── docs/
    │   ├── SRS.md              (由 Designer 产出)
    │   ├── API_Reference.md    (由 Coder 维护)
    │   └── STR_Report.md       (由 Reviewer 产出)
    └── operations/
        ├── selected/           (选品 Agent 产出)
        ├── candidate_item/     (包装 Agent 产出)
        ├── pass/               (审核通过，待上架或已上架记录)
        └── notpass/            (审核未通过，仅归档)
    ```
