# Findora

## 含义
由 Find + 某种品牌化后缀组成。
直觉上像“发现宝藏的地方”。

## 优点
- 简单
- 好记
- 有“发现、探索”的感觉
- 听起来像一个完整品牌，而不是描述性词组
- 以后可以做成平台名

## 风格
偏产品化、品牌化，比较现代。

## 风险
略有一点“已有品牌感”，所以后续要查域名和商标。

---

## 一、项目定义

### 1.1 你要做的，不是“店铺”，而是一个内容驱动的选品入口

你的核心形态应定义为：

“面向海外用户的选品内容站 / 导购站 / 个性化推荐入口。”

它不是传统电商店铺，也不是单纯联盟链接页，而是一个中间层：
- 上游：1688、Alibaba.com、以及未来可能接入的 Amazon、Temu、独立站商家
- 中游：你的内容站、选品逻辑、标签系统、AI 推荐能力
- 下游：社媒流量、订阅用户、类目偏好用户、定制化需求用户

### 1.2 你的核心价值主张

不是“我卖货”，而是：
- 我帮用户发现值得买的商品
- 我帮用户降低筛选成本
- 我帮用户做品类理解与购买判断
- 我帮用户根据偏好做持续推荐
- 最终交易在第三方商家页完成

这意味着你的站点本质是：

“内容 + 推荐 + 跳转成交”平台

而不是履约平台。

## 二、为什么本路线适合

这是我的明确判断，不是平台口号。

### 2.1 这条路更符合你的真实诉求

你前面的要求其实非常清晰：
- 你想做选品
- 你想做信息搬运 + 重组
- 你不想压货
- 你不想承担履约
- 你希望未来支持个性化推荐
- 你希望模式可以扩展，而不是绑死在某一个平台内

这天然更像一个：

“AI 驱动的内容型导购平台”

而不是阿里国际站店铺。

### 2.2 这条路的长期价值更高

联盟只是变现手段，不应该成为你的产品定义。
你的真正资产应该是：
- 域名与站点
- 内容库
- 商品标签体系
- 用户偏好数据
- SEO 入口
- 邮件/订阅用户
- 推荐算法
- 品牌心智

这套资产将来可以接多个成交平台，而不是只依赖单一佣金来源。
从商业上说，这比“纯 Affiliate 流量号”更有复利。

## 三、产品定位

### 3.1 最推荐的定位方式

我建议你把站点定位成以下三者之一，按优先级排序：

**方案 A：有趣商品发现站**

适合社媒传播，最容易起量。

特点：
- 强视觉
- 强社媒分享
- 适合 Instagram / TikTok / X
- 用户动机是“发现新鲜、有趣、便宜、稀奇的东西”

**方案 B：垂类选品站**

适合做深度和长期信任。

例如：
- kitchen gadgets
- educational toys
- pet accessories
- beauty tools
- home organization
- weird but useful products

特点：
- SEO 更容易积累
- 用户意图更强
- 更适合做订阅和定向推荐

**方案 C：AI 个性化导购站**

这是你长期最强的终局形态。

特点：
- 用户告诉你偏好
- 系统按偏好推送商品
- 可加“为什么推荐给你”
- 可加价格区间、用途、场景、人群画像

我建议：

先从 A 或 B 起步，底层按 C 的方式设计。

也就是：
前台看起来像选品内容站，后台从一开始就用标签和偏好模型来组织。

！！！最终决策：三者一起做。L1级为2C导流层，L2级为2B选品层，AI个性化推荐为底层核心。

**【核心澄清：关于“AI个性化推荐”的定义】**
这里的“AI个性化推荐”是指依靠**外部的“运营AI”**预先生成好海量商品、动态标签和推荐文案库。当用户访问或订阅时，系统底层是通过**纯数据库交叉筛选（用户标签矩阵匹配商品标签矩阵 + 随机抽取）**来呈现结果。**绝对不包含任何面向用户的实时大模型（LLM）调用**，以彻底控制成本和系统复杂度。

## 四、商业模式

### 4.1 第一阶段变现方式

前 3 个月只做两种：

**1）联盟佣金 / CPS**

用户从你的站跳转到商家页成交，你拿佣金。
Alibaba.com Affiliate 官方规则中，佣金基于 Qualifying Purchases，并以平台跟踪系统数据为准。

**2）会员订阅（后置）**

不是一开始上，而是在有一定内容量与用户反馈后再上。

会员权益可设计为：
- 每周个性化推荐
- 指定类目定向推送
- 更高频的更新
- 专属榜单 / 专属收藏夹
- AI 购买建议

### 4.2 第二阶段变现方式

等站点跑起来后，再加：
- 广告位 / sponsored placement
- 商家合作精选
- 邮件赞助
- 高级会员
- 企业采购线索服务
- 垂类咨询服务

### 4.3 最重要的原则

你的商业模型应该是：

前期靠佣金验证需求，中期靠订阅提升 ARPU，后期靠数据与品牌做复合变现。

## 五、用户路径设计

这是整个项目最关键的一环。

### 5.1 标准用户路径

**路径 1：社媒发现型**
1. 用户在 TikTok / Instagram / X 看到你的内容
2. 点进站点某篇商品页或榜单页
3. 浏览商品、图片、亮点、适用人群
4. 点击“View supplier / Check price / See details”
5. 跳转到第三方商家页成交

**路径 2：搜索型**
1. 用户 Google 搜到你的站点
2. 进入“Best xxx from China”或“Top 20 xxx gadgets”页面
3. 浏览内容
4. 点击跳转

**路径 3：订阅型**
1. 用户订阅某类目
2. 每周收到精选
3. 回站浏览
4. 跳转成交

**路径 4：个性化型**
1. 用户选择偏好标签
2. 系统生成推荐流
3. 用户收藏 / 屏蔽 / 喜欢
4. 模型逐步优化推荐
5. 跳转成交

## 七、内容策略

### 7.1 你的内容不是“搬运”，而是“重组 + 解释 + 选择”

这是成败关键。
如果只是复制商品图和标题，价值很薄，也容易有重复内容问题。

你应该把内容重写成三层：

**第一层：事实层**
- 这是什么
- 大概解决什么问题
- 基本规格
- 使用场景

**第二层：判断层**
- 为什么值得看
- 哪类用户会喜欢
- 哪些情况下不值得买
- 与常见替代品相比有什么特点

**第三层：组织层**
- 放进榜单
- 与相似商品关联
- 打标签
- 做专题集合

### 7.2 内容单元模板

每个商品页统一模板：
1. 标题
2. 一句话总结
3. Why it stands out
4. Good for
5. Watch-outs
6. Price sense
7. Related picks
8. CTA

### 7.3 内容来源

前期来源建议：
- 1688 热门商品
- Alibaba.com 对外供应商品
- 热门社媒趋势品
- 特定垂类榜单
- 节日和季节专题

注意：Alibaba.com 官方定位本身偏 B2B marketplace，所以你如果选品时直接拿大批发逻辑的商品给 C 端看，转化不一定好。你的内容层必须把“供应链视角”改写成“用户视角”。

## 九、推荐系统设计

### 9.1 第一阶段：规则推荐

先别上复杂模型。

规则推荐就够了：
- 同类目
- 同标签
- 同价格带
- 同风格
- 热门优先
- 新品加权

### 9.2 第二阶段：行为推荐

根据用户：
- 点击
- 收藏
- 停留时长
- 屏蔽
- 订阅偏好

做简单偏好加权。

### 9.3 第三阶段：基于“运营AI”预生成文案的推荐解释

**【防偏航警示】**：设计团队往往误以为“推荐解释”是在用户浏览或订阅时调用大模型实时生成的。**完全不对！本系统不包含任何面向用户的实时 LLM 调用。**

真实逻辑是：
1. **预设解释**：**外部的运营AI**在抓取商品时，就已经预先写好了各种维度下的推荐话术（例如：“推荐给你，因为你最近收藏了 budget kitchen tools” 或 “这件适合 small-space home setup”），并作为内容预先存入了数据库。
2. **纯数据库匹配**：当用户的订阅标签或浏览行为命中了对应的预设标签时，系统通过**纯数据库查询**，直接把这段预先写好的话术提取并展示出来。
3. **推流机制**：整个推荐过程本质是：`用户标签矩阵 ∩ 商品标签矩阵` -> `查询结果集` -> `随机抽选推流`。全程**零实时AI参与**，但给用户的体验依然是“AI懂我”，以此建立极低成本的壁垒。

## 十一、核心系统设计：外部“运营AI”与专属数据更新接口

**【防偏航重申】：后期的开发或设计团队极易陷入“系统包含实时AI大模型（如用户输入请求并等待AI生成）”的误区。**必须在此建立系统边界：**本系统（前台网站及底层业务）是一个没有任何实时LLM调用的、基于预生成内容的标签化内容平台。**

AI 在本项目中的真实定位，是一个独立于系统之外的**“外部运营角色（运营AI）”**。

### 11.1 外部“运营AI”的职责
运营AI 是一个跑在外部的自动化脚本或智能体。它的工作是定期的、异步的：
1. **全网选品**：去各大平台（1688、Temu、Amazon等）搜罗商品。
2. **动态定义与组合标签**：系统的标签维度和清单**不是写死在代码里的**。运营AI在分析新商品时，可以灵活组合并生成新的标签维度和标签项（例如动态生成一个新的“weird finds”标签维度）。
3. **撰写 Item Card 与推荐文章**：为每个商品预先生成详尽的“为什么好玩”、“为什么推荐”、“适合什么场景”等内容。

### 11.2 专属数据更新接口（API / CLI）
为了让上述的外部运营AI能够将工作成果推入系统，本系统必须专门设计并开放一个**运维/数据更新接口**（可以体现为 API Endpoint 或 CLI 命令的形式，如支持 `curl` 提交 JSON Payload）。

这个接口的设计必须包含：
- **严格鉴权**：必须带有 Token 鉴权机制，防止未授权访问或被伪造的AI乱改数据。
- **初始化与动态更新能力**：通过该接口，外部运营AI可以随时向系统插入新的“标签维度”、新的“标签清单”以及包含完整预生成推荐文案的“Item Card”。系统的初始数据和后续扩充都依赖此接口动态完成。

### 11.3 用户的纯数据库查询逻辑
明确了上述的输入链路后，用户的行为逻辑就非常清晰了：
1. 用户在前端选择感兴趣的标签，或者由订阅记录生成标签矩阵。
2. 系统直接拿着这个标签矩阵，通过**纯数据库查询**进行交叉筛选。
3. 对筛选出的结果集进行**随机化打乱或抽选**，最终将包含预生成推荐文案的结果展现给用户。
4. 这一过程仅仅是数据检索，快速、稳定且毫无昂贵的推理成本。

### 11.4 人类保留的控制权（非全自动环节）
虽然运营AI包揽了脏活累活，但以下环节仍需通过后台管理面板保留人工控制的权力：
- **合规与品牌调性把控**：对运营AI推送的数据进行人工 Review（或抽查）。
- **异常干预**：清洗或删除错误生成的标签和商品。
- **商业排序**：手动置顶或调整商业合作位的排序。

## 十三、合规与风险控制

这部分不能省。

### 13.1 联盟披露

如果有佣金关系，页面必须明确写：
- 这篇内容可能包含 affiliate links
- 你可能从 qualifying purchases 中获得佣金

因为 Affiliate Program 本身就是按 qualifying purchase 计佣的。

### 13.2 内容与图片使用权

不要默认可以直接搬运所有供应商图片。
要么：
- 使用可授权素材
- 使用经过处理的自有封面
- 对来源做记录
- 逐步建立自己的视觉模板

### 13.3 不做夸张承诺

不要写：
- guaranteed best
- safest
- medically proven
- official brand equivalent

尤其是保健、美容、儿童、电子类目。

### 13.4 不碰高风险类目

前期建议避开：
- 医疗器械
- 保健品
- 成人用品
- 高侵权品牌仿品
- 高安全责任商品

## 十六、90 天落地路线图

**第一阶段：0–30 天**

目标：把最小可行闭环跑通

要完成：
- 域名与站点上线
- 首页、分类页、商品页、榜单页模板
- 1 个主类目
- 50 个商品页
- 10 个榜单页
- 跳转链路
- 基础统计
- 订阅入口

结果标准：
- 有用户可以从社媒进入站点
- 可以点击跳转成交页
- 可以收集点击与订阅数据

**第二阶段：31–60 天**

目标：找到有效内容结构

要完成：
- 扩到 2–3 个类目
- 建标签体系
- 开始邮件订阅
- 开始基础推荐
- 做 1–2 套社媒模板
- 复盘高 CTR 内容特征

结果标准：
- 找到“容易点击”的类目与表达方式
- 有第一批回访用户

**第三阶段：61–90 天**

目标：开始做个性化和变现优化

要完成：
- 用户偏好选择
- 推荐 feed
- 收藏功能
- 会员页雏形
- 榜单自动化生成
- 邮件个性化推荐

结果标准：
- 站点不再只是静态内容库
- 开始具备“产品感”

## 十七、最小可行版本（MVP）定义

如果你要最聚焦，我建议 MVP 只做下面这些：

**必须有**
- 首页
- 1 个类目页
- 商品详情页模板
- 榜单页模板
- 跳转按钮
- Newsletter 订阅
- 点击统计
- 联盟披露页

**暂时不要做**
- 用户登录
- 复杂购物车
- 复杂评论系统
- 多语言
- 太重的搜索系统
- 复杂 AI 聊天导购

## 十八、最终建议：你这个项目最正确的定义

我给你一个最准确的项目定义，可以直接作为内部方案标题：

> “AI 驱动的跨境选品内容站：以内容与推荐为前台，以第三方商家成交为后台的轻资产导购平台。”

这句话基本把本质说透了：
- 不是店铺
- 不是纯媒体
- 不是纯联盟链接页
- 不是 SaaS
- 而是一个内容化、可订阅、可推荐、可扩展的交易入口

---

## 十九、我的明确判断

如果你坚持路线 B，我的建议非常明确：

先做一个“内容站外壳”，但底层按“推荐系统”来设计。

也就是：
- 用户看到的是内容站
- 你运营的是选品站
- 技术底层做的是商品数据库 + 标签系统 + 偏好推荐
- 商业上先接联盟佣金
- 长期再加订阅和个性化服务
