## 1. review of SRS

**Note：**该章节主要 review 的内容是从 Business Concept + system design 到 Findora SRS 的系统分解设计，重点考察系统分解设计是否完美覆盖业务设想。

> **本次更新（2026-04-13）**：SRS Review 团队（4人）完成全维度 Review，新增用户体验维度发现，整合业务分析师、系统架构师、数据架构师、用户体验分析师四个视角的 Review 结果。

### 1.1 结论

- 业务覆盖结论：SRS 对 Business Concept 的主干能力覆盖完整，已覆盖内容站前台（F-001~F-006）、商品与标签体系（F-010/F-011）、联盟转化链路（F-012）、订阅与偏好（F-013）、推荐系统（F-014/F-015/F-016）、运营与内容闭环（F-017/F-030）、合规约束（Section 14）与 90 天阶段目标（Section 12/13）。
- 架构覆盖结论：SRS 已显式纳入 system_design 的核心原则（统一数据 API 层、Cloudflare 技术栈、Session TTL、AI Agent 友好输出），并在 Section 3.1.4/4/8.2/11 建立了需求锚点。
- 数据体系结论：用户、商品、标签、点击、榜单、会话等核心数据实体已定义，且隐私约束（不采集完整 IP、日志保留周期、退订即时生效）已纳入验收口径。
- 用户交互覆盖：用户路径（UC-1~UC-4）完整覆盖，偏好/收藏/订阅功能基本完整，但身份演进流程需补充。
- 当前主要问题不是”缺功能”，而是”文档内状态一致性”、”部分架构落地偏差”和”接口层缺口”。

## 2. review of SDS

**Note：**该章节主要 review 的内容是根据 Findora SRS 系统设计，所有代码实现是否完美覆盖，findora SDS 的文档记录是否完整和准确。

### 2.1 结论

- 覆盖结论：SDS 已覆盖 Findora 主干模块，但还不能认定“所有代码均符合 SRS 设计并已完整更新到 SDS”。当前主要缺口集中在 F-040/F-050：SDS 仍按基线端点与既有迁移描述，而实际 `src/api/index.ts` 已挂载更多路由，`src/db/schema.ts` 也包含当前 SDS 未记录的数据模型。
- 正确性结论：本轮复核确认存在真实运行时问题，不只是文档滞后。其中至少包括 3 组路由可达性缺陷：`/api/categories/:category/subcategories`、`/api/enterprises/:id/*` 多个子路由、`GET /api/users/sessions` 会被更宽泛的父路由提前吞掉。
- 数据基线结论：F-050 当前不能视为“schema.ts + migrations 完全一致”。一部分表仅在代码里被直接访问，另一部分表在 handler 首次调用时动态创建，但 SDS 对这些情况记录不完整。
- 文档结论：SDS 当前更适合作为“模块索引”，还不能作为完整实现事实源。结合本轮检查，SDS 至少需要补齐版本基线、接口边界、迁移边界与实际运行链路说明，才能支撑“基本完成”的判断。

### 2.2 本轮关键发现

1. [x] 已review — F-002-03 子类目接口被更宽泛路由遮蔽，实际不可达
   - 证据：`src/api/index.ts` 先匹配 `GET /api/categories`，后才判断 `GET /api/categories/:category/subcategories`。任何 `/api/categories/...` 请求都会先返回 `getCategories(env)`。
   - 影响：SRS/SDS/STR 都把 F-002-03 视为已实现，但运行时请求无法进入 `getCategorySubcategories`。
2. [x] 已review — EMS 多个嵌套路由被父级通配路由遮蔽，存在真实错路由风险
   - 证据：`GET /api/enterprises/:id`、`PUT /api/enterprises/:id`、`DELETE /api/enterprises/:id` 定义在 `/api/enterprises/:id/members`、`/records`、`/audit-logs` 之前；`GET /api/users/:id` 定义在 `GET /api/users/sessions` 之前。
   - 影响：企业成员、企业记录、审计日志、会话列表等接口会被错误分发到父资源 handler，属于代码正确性问题，不是单纯 SDS 记录缺口。
3. [x] 已review — F-050 数据模型与迁移基线不一致
   - 证据：`auth.ts`、`enterprise.ts`、`record.ts`、`audit.ts`、`user.ts` 直接访问 `ems_users`、`user_sessions`、`enterprises`、`enterprise_members`、`records`、`audit_logs` 等表，但 `migrations/` 下没有对应建表语句；相反，`conversions.ts`、`email.ts`、`explain.ts` 又使用运行时 `CREATE TABLE IF NOT EXISTS`。
   - 影响：SDS 第 5 章“schema + migrations 一致”的口径不成立；在空库或新环境部署时，相关功能可能直接因缺表失败。
4. [x] 已review — SDS 与 SRS 的接口和实现口径仍有明显漂移
   - 证据：
     - SRS F-040-20 写的是 `POST /api/callbacks/affiliate`，代码/SDS 实际为 `POST /api/conversions/callback`
     - SRS F-040-21 写“每周五 10:00 UTC”，`wrangler.toml` 实际 cron 为 `0 9 * * 4`
     - SRS F-016-04 写“KV 缓存”，`explain.ts` 实际为 D1 `explanation_cache`
     - SRS F-010-05/F-040-23 描述的是系统定时抓取 `source_url`，`price_check.ts` 实际实现为“接收外部服务回推结果”
   - 影响：如果 SDS 不显式记录这些偏差，团队会持续误判真实运行链路、验收方式和联调前提。
5. [x] 已review — SDS 未完整覆盖当前代码边界
   - 证据：SDS 当前重点覆盖 Findora 主干模块，但 `src/api/index.ts` 还挂载了 auth / enterprise / record / audit / user 一整组 EMS 路由；同时 SRS 4.8 `global_configs` 在 SDS 与代码中都未落地。
   - 影响：SDS 目前无法清晰回答“哪些代码属于 Findora 正式范围、哪些属于扩展系统、哪些尚未纳入需求基线”，导致 review 和验收边界不清。

### 2.3 仍需优化点

1. [x] 已review — 先修复路由匹配顺序，再重新执行 F-002/F-040/EMS 相关端点抽检
   - 建议动作：把更具体的路由放在更宽泛的父路由之前，并补最小 HTTP 冒烟用例，至少覆盖 `categories/subcategories`、`enterprises/:id/members`、`enterprises/:id/records`、`users/sessions`。
2. [x] 已review — 补齐 EMS 与运行时建表的 SDS/F-050 记录，或将其从当前 Worker 范围剥离
   - 建议动作：二选一处理——要么为 EMS/`conversions`/`email_logs`/`explanation_cache` 补 migration + SDS 映射；要么明确标注为 out-of-scope，避免混入 Findora 正式基线。
3. [x] 已review — 统一 SRS / SDS / 代码三者的接口事实源
   - 建议动作：重点对齐 F-040-20/21/23、F-016-04 的“路径 / 调度时间 / 存储介质 / 调用方式”，不要再让 SRS、SDS、代码分别描述三套口径。
4. [x] 已review — 更新 SDS 基线版本与统计口径
   - 建议动作：SDS 至少同步到与当前 SRS/STR 一致的版本，并修正“待 AI 联调”数量、状态说明和引用的测试轮次。
5. [x] 已review — 补齐未落地的 SRS 设计项，或在 SRS/SDS 中明确降级
   - 重点对象：`global_configs`（SRS 4.8）、价格监控主动抓取链路、F-040 扩展管理接口边界。

## 3. review of STR

**Note：**该章节主要 review 的内容是根据 findora SRS 和 findora SDS 的代码实现，代码审核本身是否覆盖完整，STR 文档记录是否完整和准确。

### 3.1 结论

- 审核覆盖结论：STR 已建立连续轮次的内部审计链路，并覆盖了“编译健康（TypeScript）+关键模块抽检+遗留问题复核”的主流程，具备“内部审计报告”应有的过程可追溯性。
- 对齐结论（SRS↔STR）：STR 与 SRS 的模块级对应总体成立（F-001~F-006、F-010~F-050 均有覆盖记录），但当前主要是“模块级/样本级核验”，尚未形成对 SRS 149 项子需求的一一可追溯矩阵，外部审计视角下“完整覆盖证明”仍不充分。
- 对齐结论（SDS↔STR）：STR 引用了 SDS 的映射口径与 AI 联调SOP，但“按 SDS 模块逐项验收证据”仍偏弱，更多是结论式陈述，缺少最小证据模板（抽样端点、输入输出样例、失败路径、验收阈值）。
- 准确性结论：STR 存在多处“文档口径漂移”与“证据定位精度不足”问题，主要包括：章节基线版本残留（正文仍见 v3.06/v3.08）、审核记录顺序非时序（如第58/59次后出现第57次）、部分代码行号与描述粒度不足以稳定复核。
- 风险判断：当前问题不在“是否做了审计”，而在“审计证据是否可被第三方稳定复验”。若不收敛，会在跨团队交接时造成“看似全通过，但无法快速复算”的治理风险。

### 3.2 仍需优化点

1. [ ] 未修改 / [ ] 已修改 / [ ] 已review — 建立 SRS↔STR 一一追溯矩阵（至少到“子功能ID”粒度）
   - 当前缺口：STR 以模块级结论为主，无法直接证明 SRS 149 项子需求均被审计并可回溯到证据。
   - 建议动作：新增“需求ID→代码位置→测试/审计证据→结论→审计轮次”表，先覆盖高优先级（P0/P1）再全量补齐。
2. [ ] 未修改 / [ ] 已修改 / [ ] 已review — 建立 SDS↔STR 的证据化映射模板，替代纯结论表述
   - 当前缺口：已有模块映射，但缺“输入样例/输出样例/异常路径/阈值”四元证据，外部复验成本高。
   - 建议动作：每个核心模块至少保留1条可复算样例（请求、响应、数据库变化、日志关键字段）。
3. [ ] 未修改 / [ ] 已修改 / [ ] 已review — 统一 STR 内部基线与审计时序（版本、章节名、审核记录顺序）
   - 当前缺口：文档头部为 v3.30，但正文章节仍写 v3.06/v3.08，且审核记录顺序非时间顺序。
   - 建议动作：按“时间递增 + 轮次递增”重排记录，并统一章节基线标签为当前版本。
4. [ ] 未修改 / [ ] 已修改 / [ ] 已review — 修正“代码定位证据”精度，避免行号/路径漂移造成误审

   - 建议动作：证据改为“函数名 + 关键SQL片段/关键判断 + 提交哈希（如有）”，行号仅作为辅助。

## 4. Review of API

**Note：**该章节主要 review 的内容是 Findora API 文档（`findora_API.md`）对上游架构（Business Concept, System Design, SRS）的对齐情况，以及与下游实现（SDS, 代码）的一致性。

### 4.1 结论

- **向上对齐（Business Concept / System Design）**：API 文档在“统一 API 层、Cloudflare Worker 架构、外部运营AI可通过接口维护标签/Item Card/推荐文案”等主干方向上对齐较好。
- **向上偏差（需收敛）**：仍不能认定“完全对齐”。`system_design.md` 要求的“全局参数配置接口（如首页推荐标签、登录失效时间）”在 API 文档端点清单中仍缺少显式路径；同时 Business Concept 的“无面向用户实时 LLM 调用”与当前 API/代码中可触发 AI 生成的能力（如 explain 的 `ai=true`）存在口径冲突风险。
- **与 SRS 对齐结论**：API 文档总体跟随了当前实现口径，但与 SRS 仍有显著漂移（典型如 F-040-20 回调路径命名、F-040-23 调用方式定义），属于“API 文档与代码更一致，但与 SRS 未完全一致”的状态。
- **与 SDS/代码对齐结论**：API 文档比 SDS 更接近实际路由全貌，并且已记录一部分真实缺陷；但对“路由可达性问题”的覆盖仍不完整（新增发现 `recommendations` 与 `explain` 路由遮蔽），且个别路径仍与代码不一致（如 `/api/price-check`）。

### 4.2 与既有章节冲突处理（融合说明）

本章节原有结论中“完美承接”“忠实反映”等表述过强。本轮复核后调整为“方向对齐、细节仍有偏差”，原因如下：

1. [x] 已review — 认证口径冲突：API 文档写“用户端点用 `X-User-ID` 或 Bearer Token”，但主业务代码实际使用 `X-User-Email`/`X-Anonymous-Id`。
2. [x] 已review — 路由可达性问题不仅限于文档已列项目：除 categories/EMS 外，`GET /api/recommendations/behavioral`、`GET /api/explain/:product_id/comparison`、`GET /api/explain/:product_id/scenarios` 也会被更宽泛父路由提前吞掉。
3. [x] 已review — 外部价格接口路径不一致：API 文档列了 `/api/price-check` 与 `/api/price-check/batch`，代码仅实现 `/api/admin/price-check*`。
4. [x] 已review — API 文档“已知问题”有价值，但部分描述仍需精确化：例如 categories 问题并非被 `/api/categories/:category` 遮蔽，而是被更宽泛的 `/api/categories` 条件直接吞掉。

### 4.3 仍需优化点

1. [x] 已review — 修复路由匹配顺序并回归 API 文档可达性清单（代码优先）
   - 建议动作：按“更具体路径优先”重排 `src/api/index.ts`，至少覆盖 `categories/subcategories`、`recommendations/behavioral`、`explain/*/comparison|scenarios`、`enterprises/*`、`users/sessions`。
2. [x] 已review — 统一 API 文档与代码的认证契约
   - 建议动作：二选一处理——要么代码新增 `X-User-ID/Bearer` 支持，要么 API 文档改为 `X-User-Email`/`X-Anonymous-Id` 为准并说明演进计划。
3. [x] 已review — 收敛外部系统路径口径（SRS / API / SDS / 代码）
   - 建议动作：集中对齐 F-040-20/F-040-23：回调路径命名、是否 admin 前缀、是“主动轮询”还是“外部回推”。
4. [x] 已review — 补齐 System Design 要求的“全局配置管理接口”映射
   - 建议动作：明确 `global_configs` 的 API 契约（读写端点、鉴权、审计），并同步到 SRS/SDS/API 文档与实现。
5. [x] 已review — 处理“无用户侧实时LLM”与当前 AI 接口能力的口径冲突
   - 建议动作：若坚持 Business Concept 路线，需限制用户入口触发实时 AI 生成（如 explain 的 AI 开关），并在 API/SRS/SDS 中统一标注为“仅运营侧异步生成”。
