1. 引言

1.1 目的

本文档定义一套软件工具，实现对大型 Markdown 文件的高效按区块随机读取与写入，并通过 Model Context Protocol (MCP) 将能力暴露给 AI 大模型（Agent）。该工具旨在作为“OAIA Agent工作流”（研发循环、运营循环、管理循环）的核心文档载体，使 AI 能够在不加载整个文件的前提下，精准操作 Markdown 文件中的指定段落。

1.2 范围

· 包含：
  · 一个纯 Python 核心库 markdown-indexer，提供 Markdown 文件的索引构建、按层级路径读取区块、按路径写入区块的能力。
  · 一个基于 mcp 协议的服务器 mcp-markdown-workflow，将上述能力封装为可供大模型调用的工具。
  · 支持多级标题层级（至少三级，架构上不限制层数）。
  · 针对文件大小在 100MB 以内的高效读写，且索引构建时间可忽略。
· 不包含：
  · 并发写入控制、文件锁定机制（初期假设单进程访问）。
  · Markdown 格式校验、前端界面。
  · 版本控制集成（如 Git），但工具本身与版本控制可共存。

1.3 术语与定义

· 区块：一个 Markdown 标题（#、##、###…）及其下方直到下一个同级别或更高级别标题之间的全部正文内容。
· 路径：由各级标题文本组成的有序列表，例如 ["SRS", "功能需求", "需求1.1"]，用于唯一标识一个二级或三级区块。路径的第一个元素为一级标题，依次类推。
· 索引：在内存中维护的一棵树状结构，记录每个标题的层级、标题文本、在文件中的字节偏移以及子节点映射。
· MCP (Model Context Protocol)：AI 模型调用外部工具的标准化协议，本工具作为 MCP Server 运行。

1.4 参考文献

· Model Context Protocol 官方文档
· Python mcp 库
· Markdown 语法规范 (CommonMark)

2. 总体描述

2.1 产品视角

系统由两个组件构成：

1. 核心库 markdown-indexer：无状态函数集合，直接操作 Markdown 文件，提供构建索引、读取、写入功能。不依赖 MCP，可被任何 Python 程序调用。
2. MCP Server mcp-markdown-workflow：依赖核心库，遵循 MCP 协议，通过标准输入/输出（Stdio）与 AI 客户端通信。启动时加载指定工作目录中的 Markdown 文件索引，并对外暴露三个工具：get_outline、read_block、write_block。

系统与外部交互如下：

```
AI Agent (客户端)
    ↕ MCP 协议 (Stdio)
MCP Server (mcp-markdown-workflow)
    ↕ 函数调用
核心库 (markdown-indexer)
    ↕ 文件 I/O
Markdown 文件 (研发.md / 运营.md / ...)
```

2.2 用户特征

· 直接用户：AI 大模型（Agent），通过工具调用间接使用。
· 间接用户：开发者、工作流设计者，通过编写提示词或调用 MCP 客户端使用。
· 所有用户假设熟悉 Markdown 标题结构，并能按约定命名标题（中文或英文均可）。

2.3 运行环境

· 操作系统：Windows、macOS、Linux（Python 3.10+ 兼容环境）。
· 硬盘：要求 SSD 或机械硬盘均可，文件读写性能见后文。
· 内存：索引和一小部分区块内容驻留，10MB 文件索引内存 < 1MB。
· 软件依赖：
  · mcp 协议库
  · 标准库 mmap, os, json（核心库无额外依赖，MCP Server 仅依赖 mcp）

2.4 假设与依赖

· 目标 Markdown 文件使用 UTF-8 编码，且标题行以 # 开头，后跟至少一个空格或制表符。
· 文件大小不超过 100MB（超过亦可运行，但写入策略“全量加载写回”可能导致短暂延迟）。
· MCP Server 所在进程能够持续运行，且在写入操作期间其他进程不会同时修改同一文件（单进程访问）。
· 标题文本在文件内具有唯一性（若重复，路径解析可能产生歧义；设计上要求用户在生成文档时保证同级标题唯一）。

3. 具体需求

3.1 功能需求

3.1.1 索引构建

· 输入：文件路径（相对或绝对）。
· 处理：
  · 以只读、二进制模式打开文件。
  · 逐行扫描，识别所有以 # 开头且#后紧跟空格或制表符的行。
  · 根据连续 # 个数确定标题级别（如 # 为1级， ## 为2级， ### 为3级）。
  · 记录每个标题行的字节起始偏移（即该行的第一个字节在文件中的位置）。
  · 构建树状索引结构，键为标题完整文本（去除首尾空白），值为一个节点，节点包含：
    · title: 标题文本（不含 #）
    · offset: 该标题行的字节偏移
    · subs: 子节点字典，键为子标题文本。
  · 返回根节点下的所有一级标题子节点组成的字典（虚拟根节点不导出）。
· 输出：Python 字典，表示文档的层级索引。
· 性能：对 100MB 文件，索引构建时间 < 100ms（取决于磁盘速度）。

3.1.2 按路径读取区块

· 功能名称：read_block(filepath, path)
· 输入：
  · filepath: 字符串，Markdown 文件路径。
  · path: 字符串列表，如 ["SRS", "功能需求", "需求1.1"]。
· 处理：
  · 调用索引构建（若未缓存则新建，但 MCP Server 可缓存索引）。
  · 从索引中按路径逐层查找节点：
    1. 在一级子节点中匹配 path[0]。
    2. 在匹配到的一级节点的 subs 中匹配 path[1]，以此类推。
  · 若路径不存在，返回错误信息。
  · 若路径存在，获取该节点对应的 offset。
  · 从该偏移开始读取文件内容，截取区块：
    · 区块从该标题行的下一行开始，直到遇到下一个相同或更高层级的标题行为止（或文件末尾）。
    · 区块内容不包含起始标题行本身。
· 输出：字符串，为该区块的 Markdown 正文（不含标题）。
· 异常：路径无效时返回预定义错误文本，提示“指定章节未找到”。

3.1.3 按路径写入区块

· 功能名称：write_block(filepath, path, new_content)
· 输入：
  · filepath: 字符串，文件路径。
  · path: 字符串列表，目标区块路径。
  · new_content: 字符串，新的 Markdown 正文（可包含多行，不含标题行）。
· 处理：
  1. 调用索引构建，获得完整索引。
  2. 找到目标节点，确认路径有效。
  3. 全量加载：将整个文件读取为字符串，或以行列表加载（保留换行）。
  4. 定位原区块正文范围：从标题行的下一行开始，到下一个同级或更高级标题行之前结束。
  5. 将原区块范围内的内容整体替换为 new_content，并适当处理换行。
  6. 将修改后的所有内容写回原文件（覆盖）。
· 输出：成功时返回操作确认消息（如“区块已更新”）；失败时返回错误描述。
· 原子性：初期采用“整体写入”策略，写入过程中若发生异常可能导致文件损坏。建议使用时确保备份，未来版本可升级为“先写临时文件再重命名”以增强安全性。
· 限制：仅替换正文，不修改标题行。

3.1.4 获取文档大纲

· 功能名称：get_outline(filepath)
· 输入：文件路径。
· 处理：构建索引后，提取每个节点的标题和层级，生成简洁的树形文本列表（剔除偏移等内部信息）。
· 输出：字符串，展示为：
  ```
  # SRS
    ## 功能需求
      ### 需求1.1
      ### 需求1.2
    ## 非功能需求
  # SDS
    ...
  ```
· 用途：供大模型快速了解文档结构，便于后续精确调用 read_block/write_block。

3.1.5 MCP 工具接口

· 在 MCP Server 中，上述功能暴露为三个 @server.tool() 装饰的工具：
  · get_outline(filepath: str) -> str
  · read_block(filepath: str, path: list[str]) -> str
  · write_block(filepath: str, path: list[str], content: str) -> str
· MCP Server 启动时会配置一个工作根目录（通过环境变量 WORKSPACE_PATH），允许 filepath 参数仅使用相对路径以增强安全性；若需要绝对路径也可配置。

3.2 外部接口需求

3.2.1 MCP 协议接口

· 遵循 MCP 规范，使用 Stdio 传输。
· 客户端初始化连接时，服务器声明以上三个工具的工具列表。
· 工具调用接收 JSON 格式的参数，返回文本内容。
· 错误处理：参数缺失或文件不可访问时返回人类可读的错误信息，模型能够理解。

3.2.2 文件系统接口

· 核心库直接通过 Python 文件操作 API 访问本地文件，不涉及网络。
· 文件路径支持相对路径（相对于进程工作目录）和绝对路径。

3.3 性能需求

指标 要求 备注
索引构建时间 (100MB) ≤ 500ms 首次构建，单次扫描
缓存索引后读取区块 ≤ 5ms 仅 seek + 顺序读至区块结束
写入区块 (10MB 文件) ≤ 200ms 全量加载、修改、写回
内存占用（索引结构） ≤ 5MB 1000 个标题节点的极端情况

3.4 设计约束

· 实现语言：Python 3.10+（核心库纯粹使用标准库，无第三方依赖；MCP Server 依赖 mcp 库）。
· 代码风格：遵循 PEP8，类型提示可选但建议。
· 日志：使用标准 logging 记录关键操作（读取/写入），便于调试。

4. 功能详述与交互流程

4.1 内部索引数据结构（Python 示例）

```python
{
  "# SRS": {
    "title": "SRS",
    "offset": 0,
    "subs": {
      "## 功能需求": {
        "title": "功能需求",
        "offset": 56,
        "subs": {
          "### 需求1.1": {
            "title": "需求1.1",
            "offset": 124,
            "subs": {}
          }
        }
      }
    }
  },
  "# SDS": { ... }
}
```

4.2 读取流程

1. AI 模型调用 get_outline("研发.md") 获取大纲，选择目标。
2. AI 调用 read_block("研发.md", ["SRS", "功能需求", "需求1.1"])。
3. MCP Server 从缓存或实时索引中找到 offset = 124。
4. 用 mmap 或 seek 定位到偏移 124，顺序读取直到遇到下一个 #、## 或 ### 行。
5. 返回抽取的正文文本。

4.3 写入流程

1. AI 生成新内容后，调用 write_block("研发.md", ["SRS", "功能需求", "需求1.1"], new_text)。
2. Server 通过索引确定该区块的起始标题行偏移和内容范围。
3. 读取整个文件到内存（字符串或 list[bytes]）。
4. 截取区块前后的部分，拼接 标题行 + "\n" + new_text + "\n" + 后文。
5. 在临时变量中完成全部拼接，确认无误后一次性写回原文件。
6. 写回成功后，可选择清除索引缓存（若文件最后修改时间变化），下次调用时重新扫描。

4.4 MCP 工具调用示例

假设 AI 需要了解研发文档的 SRS 部分并补充某个需求：

```json
[
  {"tool": "get_outline", "arguments": {"filepath": "研发.md"}},
  {"tool": "read_block", "arguments": {"filepath": "研发.md", "path": ["SRS", "功能需求", "需求1.1"]}},
  // 模型基于读到的内容生成补充描述，然后：
  {"tool": "write_block", "arguments": {"filepath": "研发.md", "path": ["SRS", "功能需求", "需求1.1"], "content": "更新后的需求描述..."}}
]
```

5. 非功能需求

5.1 可靠性

· 写入操作因使用全量覆盖，需考虑最小化数据丢失风险。建议请求端在写入前可请求调用 read_block 备份原内容。
· 工具应记录每一次写入的操作日志（时间、路径、内容长度），便于回溯。

5.2 可维护性

· 核心库 markdown-indexer 应提供完整的单元测试（使用临时文件模拟各种层级结构）。
· MCP Server 的配置项（工作路径、文件扩展名过滤等）通过环境变量或配置文件设置。

5.3 可扩展性

· 索引构建逻辑与标题层级无关，可自动适配任意深度的标题。
· 未来可增加“文件监视器”，当 Markdown 文件被外部修改时自动重建索引。
