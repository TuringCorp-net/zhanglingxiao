## 一、核心设计理念：创作流水线

### 1.1 问题本质

长篇创作的天然困境：

> LLM 写短文（<2000 字）没问题，但写长篇（>2万字）必然出现**逻辑断裂、人设漂移、伏笔遗忘**。

这不是模型能力问题，而是**上下文管理问题**。人类作者写长篇也不是一口气写完——他们依赖大纲、人物小传、伏笔笔记、反复修订。AI 写作需要同样的工程化支撑。

### 1.2 Story Forger 的解法

将创作过程系统化为一条**有明确前后顺序、双向约束、可迭代**的创作流水线：

```
M0 原始构想 → M1 世界观 → M2 长篇框架 → M3 人物卡 → M4 伏笔账本 → M5 章节意图 → M6 章节编写
  │             │          │            │           │            │          │
  └─────────────┴──────────┴────────────┴───────────┴────────────┴──────────┘
                                    ▲
                          任意节点可回溯修改
                          下游模块自动触发重校验

M0 特殊规则：Story Elf 禁止修改。外部 AI/Agent 视为作者，可正常读写。
```

**核心原则**：

1. **从粗到细**：世界观（最粗）→ 主线 → 人物/伏笔 → 章节意图 → 章节正文（最细）。每一层增加细节，但绝不违背更粗层的约束。
2. **双向链接**：下游依赖上游的约束；上游修改后，下游自动感知需要重新校验。
3. **同一流程，同一 API，同一质量门禁**：外部 AI Agent 和人类作者使用完全相同的接口和工作流。人类作者的路径是「自由编辑区写初稿 → Story Elf 分析 → 建议拆分到槽位 → 作者确认」；外部 Agent 走同样的路径。Agent 只需往 `free_content` 写入 Markdown 文章，Story Elf 负责将文章内容拆解到结构化槽位中。这意味着 Agent 无需学习每个模块的内部模板结构（slot ID、section 划分），只需专注于写出好的内容。
4. **Story Elf 是结构化桥梁**：自由文本与模板槽位之间的转换由 Story Elf 完成，而非由外部 Agent 手工填写。这降低了 Agent 的接入门槛（只需写文章，不需填表单），同时保证了结构化质量（Story Elf 是唯一的结构化入口，不会出现外部 Agent 填错 slot 的问题）。
5. **持续迭代**：这不是"一次填完就写完"的线性流程。作者可以随时回到世界观修改规则，系统自动标记受影响的下游资产。

## 二、六大模块定义

### 模块总览

| 序号 | 模块 | 核心产出 | 粒度 | 依赖 |
|------|------|---------|------|------|
| M0 | 原始构想 | Original Concept（单槽位模板，`content` slot） | 自由形式 | 无（纯粹的作者灵感记录） |
| M1 | 世界观/设定引擎 | Setting Bible（设定圣经） | 世界级 | M0（参考） |
| M2 | 主线剧情引擎 | Main Plot（主线大纲）+ 分幕结构 | 全局级 | M0, M1 |
| M3 | 人物卡系统 | Character Cards（核心人物 + 章节人物） | 角色级 | M1, M2 |
| M4 | 伏笔账本引擎 | Foreshadowing Ledger（伏笔暗线规划与追踪） | 跨章级 | M2, M3 |
| M5 | 章节意图卡 | Chapter Intent Card（每章蓝图） | 章节级 | M1-M4 |
| M6 | 章节生产流水线 | Draft v0 → Check → Polish → Draft v1 | 段落级 | M1-M5 |

### M0：原始构想

**产出**：Original Concept（`original_concept.md`）

**内容范围**：
- 无任何模板或结构约束——纯自由文本
- 创作者可以任意格式、任意内容记录灵感碎片、创作冲动、初步构思
- 允许口水话、凌乱、跳跃、甚至自相矛盾——这些都是宝贵的原始创意记录
- 作为后续 AI 生成 M1-M6 的原始输入参考

**在流水线中的角色**：
- 这是整个创作流水线的**最前端入口**，位于世界观之前
- M1-M6 的 AI 生成可以以此为参考上下文，但 M0 本身不由 AI 产生
- 创作者可以随时回溯翻阅 M0，从最初的闪光思想中汲取灵感
- 即使创作到后期，M0 仍然是一个"回看初心"的锚点

**特殊规则（不可妥协）**：

| 规则 | 说明 |
|------|------|
| **Story Elf 禁止修改** | Story Elf（内部辅助 AI）不得以任何方式修改 M0 内容。外部 AI/Agent 视为作者，可正常使用 PUT 端点 |
| **无模板约束** | 不同于 M1-M6 的结构化模板，M0 初始化为完全空白的 `.md` 文件，作者随意书写 |
| **开放读写** | M0 端点通过 Bearer Token 认证。人类作者和外部 AI/Agent 均可读写。仅 Story Elf 被设计层面排除写入权限 |
| **初始状态** | 作品创建时即在 R2 初始化空白的 `original_concept.md`，作者随时可写 |

**AI 参与方式**：
- **Story Elf（内部辅助 AI）**：**绝不**在 M0 阶段参与——不扩写、不整理、不建议修改。可在 M1-M6 阶段读取 M0 内容作为参考上下文（通过 API），但输出写入 M1-M6，绝不写回 M0
- **外部 AI/Agent**：视为作者，可通过 PUT 端点自由读写 M0。创作者可让外部 Agent 帮助整理原始构想，Agent 的输出写入 M0
- 创作者可对 Story Elf 说"参考我的原始构想生成世界观"，Story Elf 会读取 M0 作为输入，但输出写入 M1（世界观），绝不写回 M0

**M0 文件格式**：
- 标准 Markdown 文件（`.md`）
- 存储在 R2：`works/{id}/{lang}/original_concept.md`
- 初始化为空白——名副其实的"空白画布"
- 作者可以自由使用任何 Markdown 语法（标题、列表、引用等），但系统不强制任何结构

### M1：世界观/设定引擎

**产出**：Setting Bible（`world_bible.md`）

**内容范围**：
- 世界规则与边界：力量体系、技术体系、社会组织、禁忌与代价
- 核心主题与价值观：作品要传达的核心命题、情感基调
- "承诺清单"：开篇对读者许诺的爽点/价值，后续必须兑现
- 禁区与风格：不能触碰的内容、语言风格、节奏偏好

**在流水线中的角色**：
- 这是**最高约束**——所有后续模块的内容必须服从设定圣经
- 可以版本化、可回滚
- 作为一致性校验的"规则库"

**AI 参与方式**：
- 作者提供原始构想（M0）或一句话概念
- AI 读取 M0 作为参考上下文，扩写为结构化的设定圣经
- 作者可以直接编辑圣经的任意部分
- 修改后，系统标记"世界观已变更"，触发下游模块的兼容性提示

**Setting Bible 固化模板**：

这是 Story Forger 差异化竞争力的核心体现。不同于"给 AI 一个空白文档让它自由发挥"，Story Forger 将世界观的**结构框架**固化下来。即使内容为空，框架本身也是完整的——这给了作者和 AI 一个明确的"填空题"，而非"命题作文"。


**模板的设计意图**：

| 意图 | 说明 |
|------|------|
| 给 AI 的提示 | 有了结构化框架，AI 知道在哪个标题下写什么内容，生成质量更高、更聚焦 |
| 给作者的引导 | 新作者可能不知道"世界观"包含什么——框架本身就是一份 checklist |
| 一致性校验的基础 | M6 的一致性校验可以按章节定位约束："检查本章是否违反《一、世界规则与边界》中的某条规则" |
| 版本化粒度 | 每个二级标题下的内容可独立追踪变更，而非整个文件一体的 diff |

**模板的生命周期**：
1. 作品创建时 → `world_bible.md` 初始化为上述空模板（框架完整，内容为空）
2. 作者手动填写 / AI 生成 → 各章节逐步填充
3. 版本迭代 → 每次修改记录版本，可回滚到历史版本

### M2：长篇框架引擎

**产出**：长篇框架大纲（`outline.md`）— 主线/支线的阶段划分、阶段目标、高潮与反转、节奏计划

这是 original_concept 中"模块二：目录与长篇框架引擎"的完整工程化实现。它不是简单的大纲，而是一个**可自我完善的结构规划系统**。

**内容范围**：
- **故事概览**：一句话梗概、故事类型、核心冲突
- **主线阶段划分**：三幕（或五幕/多卷）结构，每幕的阶段目标、关键事件、幕末转折
- **支线规划**：支线与主线的关系、独立价值
- **节奏计划**：章节→阶段→情绪曲线映射，为日更/周更服务
- **关键转折点**：不可逆的情节拐点清单
- **伏笔埋设计划**：跨章节伏笔的整体布局

### M3：人物卡系统

**产出**：Character Cards（`entities` 表 + `characters/*.md`）

**分层策略**：

| 层级 | 定义 | 诞生时机 | 详细程度 |
|------|------|---------|---------|
| 核心人物 | 主角、主角团、大反派 | 与 M2 主线几乎同时诞生 | 完整的动机、能力、成长弧、关系网 |
| 阶段人物 | 某一幕/某一卷的重要角色 | 分幕确定后细化 | 阶段性动机、与核心人物的关系 |
| 章节人物 | 只在特定章节出现的功能角色 | 编写该章节时创建 | 简要设定，服务于本章情节 |

**与 M1/M2 的关系**：
- 人物能力边界受 M1 世界规则限制（如"这个世界没有复活术"→ 人物不能有复活能力）
- 人物动机必须服务于 M2 的主线冲突

> **M0 的特殊位置**：M0 为 M1-M6 提供"参考上下文"而非"约束"。Story Elf 可读取 M0 来理解作者的原始意图，但 M0 内容不构成一致性校验的规则来源——只有 M1（设定圣经）才是最高约束。Story Elf 禁止修改 M0；外部 AI/Agent 视为作者，可正常读写。

### 3.2 回溯修改的涟漪效应

当作者修改某个模块时，系统自动识别受影响的"下游"资产：

| 修改位置 | 受影响模块 | 处理方式 |
|---------|-----------|---------|
| M1 世界观（改规则） | M2 M3 M4 M5 M6 | 标记"世界规则已变更"。M6 中已完成章节标记为 ⚠ 需重新校验。 |
| M2 主线（改剧情走向） | M4 M5 M6 | 伏笔回收窗口可能需要调整。未写章节的意图卡可能需要重新生成。 |
| M3 人物（改人设） | M4 M6 | 涉及该人物的已完成章节标记为 ⚠。伏笔中涉及该人物的条目标记为待复核。 |
| M4 伏笔（改回收点） | M5 M6 | 受影响章节的意图卡标记为"伏笔约束已变更"。 |

**设计原则**：修改不自动传播（不自动改写已完成章节），而是**标记 + 提示**。作者决定如何处理受影响的内容。

### 3.3 模块间的关系矩阵

```
         M1     M2     M3     M4     M5     M6
        世界观  主线   人物   伏笔   意图   章节

M1       -     约束   约束   间接   间接   终审
M2     反馈     -     约束   约束   约束   约束
M3     反馈   反馈     -     双向   约束   约束
M4      无    反馈   反馈     -     约束   约束
M5      无     无     无     无      -     指令
M6      无     无    反馈   反馈   反馈     -
```

- **约束**（行→列）：行模块为列模块提供约束
- **反馈**（行→列）：列模块的执行结果可能触发对行模块的修改建议
- **间接**：通过其他模块传递约束

## 四、作者的创作旅程

### 4.1 推荐流程（首次创作）

```
阶段 0：原始构想（M0）
  作者在 M0 面板中自由记录灵感碎片、创作冲动、初步构思。
  无模板、无格式约束——纯粹的个人创意空间。Story Elf 禁止修改此内容。
  这是所有后续工作的种子，也是创作全程可回溯的"初心锚点"。

阶段 1：世界观定型（M1）                                   [预计：多轮迭代]
  1. AI 根据原始概念，扩写为结构化 Setting Bible
  2. 作者审阅、直接编辑、或提出修改方向
  3. AI 再次调整
  4. 重复 2-3，直到世界观基本稳定
  产出：Setting Bible v1（可继续迭代）

阶段 2：主线剧情定型（M2）                                 [预计：多轮迭代]
  1. AI 根据世界观，生成主线剧情草案（几百字的走向描述）
  2. 作者审阅、调整剧情走向和转折点
  3. AI 生成分幕/分阶段结构
  4. 作者调整节奏和结构
  产出：Main Plot + 分幕大纲

阶段 3：核心人物设定（M3）                                 [与 M2 交叉]
  1. AI 从主线剧情中识别需要的人物，生成核心人物卡
  2. 作者审阅、调整人设
  3. 人物关系网可视化确认
  产出：核心人物卡（>=3 张）

阶段 4：伏笔与冲突规划（M4）                               [依赖 M2+M3]
  1. AI 根据大纲和人物关系，帮助规划伏笔网络（至少 3 条核心伏笔）
  2. 作者审阅、调整每条伏笔的类型、强度、埋种章节、发展路径和回收计划
  产出：伏笔账本（结构化 Markdown 模板）

阶段 5：逐章编写（M5 → M6）                                [循环执行]
  对每一章：
  1. AI 生成意图卡 → 作者确认
  2. AI 生成初稿 Draft v0
  3. 一致性校验 → 查看问题清单
  4. AI 润色 → 或作者手动修改
  5. 输出中稿 Draft v1
  6. 资产更新（人物状态、伏笔状态、时间线）
  产出：完成的章节

阶段 ∞：持续迭代
  作者随时可以回到阶段 1-4 修改任何设定
  系统自动标记受影响的下游资产
```

### 4.2 创作模式

Story Forger 支持两种创作模式：

| 模式 | 流程 | 适合 |
|------|------|------|
| **流水线模式** | 严格遵循 M1→M2→M3→M4→M5→M6 顺序，每个阶段定型后进入下一阶段 | 第一次创作、需要系统性规划的长篇 |
| **跳跃模式** | 从任意模块开始，边写边补充上游设定 | 有经验的作者、已有构思、快速原型 |

两种模式共享同一套约束校验机制——跳跃模式下，如果缺少上游设定，一致性校验会标记"无约束可引用"（而非报错），作者可以后续补充。

## 五、AI 的参与角色

> **术语约定**：此处描述的"AI"指 **Story Elf（故事精灵）**——Story Forger 内置的辅助创作 AI。Story Elf 扮演扩写者、校验者、建议者三种角色，体现小精灵般灵动、有魔法、可爱的特质。外部 AI/Agent 视为**作者**，享有全部 API 权限（包括 M0），不在此处讨论范围内。

### 5.1 扩写者（Expander）

将作者的简短输入扩展为结构化内容。

| 场景 | 输入 | 输出 |
|------|------|------|
| M1 | 一句话概念 / M0 原始构想 | 结构化 Setting Bible |
| M2 | 世界观 + 创作意图 | 主线剧情 + 分幕结构 |
| M3 | 主线剧情 | 核心人物卡 |
| M4 | 大纲 + 人物 | 伏笔暗线规划与追踪 |
| M5 | 大纲 + 伏笔状态 | 本章意图卡 |
| M6 | 意图卡 + 所有约束 | 章节正文 |

### 5.2 校验者（Validator）

以规则库为基准，检测矛盾和不一致。

- M6 一致性校验：逐条对照 M1-M4 的约束
- 跨章节校验：检测人物漂移、时间线矛盾、伏笔遗忘
- 设定冲突检测：当作者修改 M1 时，自动检查已完成章节是否有违反新规则的段落

### 5.3 建议者（Advisor）

提供创作建议，不代替作者决策。

- 节奏分析：当前章节序列的紧张/松弛节奏是否合理
- 爽点密度：关键情绪回报的分布是否均匀
- 人物使用率：是否有核心人物长期未出场
- 伏笔健康度：未回收伏笔数量是否过多、是否有"死伏笔"

### 5.4 Story Elf 的边界

Story Elf 的设计约束：

| 边界 | 说明 |
|------|------|
| **M0 禁令** | Story Elf **绝不**修改 M0（原始构想）。可读取 M0 作为 M1-M6 的参考上下文，但写入目标永远是 M1-M6 |
| **不替代作者决策** | Story Elf 扩写、校验、建议，但最终决定权在作者。校验标记矛盾但不阻断写作 |
| **不自动传播修改** | 上游变更时，Story Elf 标记受影响的下游资产但不自动改写。作者决定如何处理 |

## 五-B、Story Elf：Context-Aware 浮动 AI 伴侣

### 设计意图

Story Forger 不仅是一个写作工具——它通过 **Story Elf** 为读者和作者提供了一个始终在身边的 AI 伴侣。Story Elf 是横跨 Read / Write 两侧的浮动组件，以 IP 形象（小精灵）呈现，可拖拽至屏幕任意位置。**位置跨页面保持**（localStorage），切换 Read ↔ Write 时不跳变，给用户一致的"同一个小精灵在陪伴我"的体验。

### 两侧角色

| 侧 | 角色 | 核心能力 |
|----|------|---------|
| **Read（阅读侧）** | 伴读精灵 | 根据阅读位置提供分析、解答疑问、推荐相关内容 |
| **Write（写作侧）** | 写作精灵 | 一致性检查、写作建议、对话式润色、灵感讨论 |

两侧共享同一套视觉形象和浮动交互，但 AI 行为不同——Read 侧侧重"理解和推荐"，Write 侧侧重"校验和生成"。

### 核心机制：上下文感知（Context-Aware）

Story Elf 的差异化竞争力在于**不需要用户复制粘贴**。用户在哪个页面、读哪篇文章的哪一章、写哪个模块的什么内容——这些上下文由页面自动传递给 Elf：

```
┌─────────────────────────────────────────────────────┐
│                    StoryElf.setContext({             │
│  page: 'read' | 'write',                           │
│  work_id: '...',                                    │
│  work_title: '...',                                 │
│  section_id: '...',      // 阅读/写作中的章节       │
│  section_title: '...',                              │
│  panel: 'worldbuilding' | 'characters' | ...        │
│                    })                                │
└─────────────────────────────────────────────────────┘
```

**Read 侧场景**：读者在阅读第 3 章第 5 段时，对 Elf 说"这段我不太理解"。Elf 已经知道 `work_id` 和 `section_id`，可以直接读取对应内容给出分析——读者不需要复制粘贴原文。

**Write 侧场景**：作者正在编辑「世界观」面板，对 Elf 说"我没什么思路，有什么建议吗？"。Elf 知道用户当前在 `worldbuilding` 面板，可以基于已有设定圣经内容给出建议——作者不需要说明"我在写世界观"。

### 技术实现

- `story-elf.js`：自包含组件，CSS + HTML + 拖动逻辑 + 位置持久化全部封装
- 任何页面只需 `<script src="/story-elf.js"></script>` 即可获得 Elf
- `window.StoryElf` 全局 API：`toggle()`, `addMessage()`, `sendChat()`, `setContext()`, `getContext()`, `setActions()`
- Write 页面通过 `StoryElf.sendChat` 覆盖和 `StoryElf.setActions()` 注入写作侧专属按钮
- 位置通过 `localStorage('sf_elf_pos')` 持久化，跨 Read/Write 保持

### 设计原则

| 原则 | 说明 |
|------|------|
| **自包含** | 单一 JS 文件，不污染页面，不依赖页面已有结构 |
| **上下文透明** | 页面自动传上下文，用户无需手动告知 AI 当前状态 |
| **位置持续** | 用户拖到哪里就停在哪里，切页面/切语言不跳变 |
| **角色双面** | 同一形象，Read 侧和 Write 侧分别扮演不同角色 |
| **低侵入** | 默认收起的对话框，不遮挡内容；点开才交互 |

### 私有知识库

Story Elf 后端可访问 R2 私有路径 `system/case_knowledge/` 下的结构化叙事分析资料。这些资料作为 Elf 的灵感与技艺参考，在辅助作者时可按需检索并以匿名化方式注入对话上下文。资料中引用的具体作品名称与作者信息不对外暴露。

点 Pipeline 胶囊切换模块，下方左右分栏自动加载对应内容：

## 七、写作引导流程（Pipeline Guide）

### 7.1 设计意图

长篇创作的最大障碍不是"不会写"，而是"不知道该从哪开始、下一步该做什么"。

Story Forger 的流水线本身就是一个结构化的创作步骤。将此流水线可视化为一个**始终可见的引导条**，让作者在任何时候都能看到：
- 当前在哪个阶段
- 哪些阶段已完成
- 建议下一步做什么

### 7.2 引导条设计

```
┌──────────────────────────────────────────────────────────────────────┐
│  创作引导：                                                           │
│  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐     │
│  │ ✓ 构想 │ → │ ✓ 世界 │ → │ ✓ 主线 │ → │ ○ 人物 │ → │ ○ 伏笔 │ ... │
│  │  M0    │   │  M1    │   │  M2    │   │  M3    │   │  M4    │     │
│  └────────┘   └────────┘   └────────┘   └────────┘   └────────┘     │
│  有灵感       已完成        已完成        当前步骤      待开始         │
└──────────────────────────────────────────────────────────────────────┘
```

**交互规则**：
- 引导条始终显示在 Story Forger 页面顶部（工具栏下方）
- 每个步骤显示：模块名、状态图标、简短标签
- 当前步骤高亮，已完成步骤打勾
- 点击任意步骤 → 跳转到对应面板/模块
- 对于全新作品，M1 高亮为"建议从这里开始"

**步骤状态判定**：

| 状态 | 图标 | 判断条件 |
|------|------|---------|
| 已完成 | ✓ | 对应模块的核心产出文件存在且有实质内容 |
| 进行中 | ● | 有内容但不完整（如模板已填充部分章节） |
| 待开始 | ○ | 对应产出为空（仅有模板框架） |

### 7.3 与模块面板的联动

点击引导条的步骤 → 触发对应操作：

| 步骤 | 点击行为 |
|------|---------|
| M0 原始构想 | 展开左活页夹的原始构想面板，展示自由文本编辑器 |
| M1 世界观 | 展开左活页夹的世界观面板，若为模板则展示结构化框架 |
| M2 主线剧情 | 展开总纲面板，若未生成则提示 AI 生成 |
| M3 人物卡 | 展开人物树面板 |
| M4 伏笔账本 | 展开伏笔账本面板 |
| M5 章节意图 | 切换到软木板视图（鸟瞰各章节） |
| M6 逐章编写 | 展开章节树面板 |

## 十、多语言架构设计

### 10.1 设计目标

Story Forger 面向全球创作者服务。**中文 + 英文**是主力市场，其他语种（日/韩/法等）为按需扩展。

核心原则：**一套代码，多语言路径，零额外复杂度**。

### 10.2 R2 存储路径设计

每个语言的产出物存储在独立子目录中：

```
works/{work_id}/
├── zh/   ← 中文版（默认）
│   ├── world_bible.md
│   ├── outline.md
│   ├── chapters/ch_*.md
│   └── ...
├── en/   ← 英文版
│   ├── world_bible.md
│   ├── outline.md
│   ├── chapters/ch_*.md
│   └── ...
└── ja/   ← 日语（未来扩展）
```

**扩展新语种**：只需在 `SUPPORTED_LANGS` 数组中添加语言代码，并提供对应模板。

### 10.3 API 语言参数

所有 Story Forger Write API 通过 `?lang=` query 参数指定目标语言：

```
GET  /api/write/worldbuilding/{work_id}?lang=en  → 返回英文版
POST /api/write/worldbuilding/generate?lang=zh   → 生成中文版
PUT  /api/write/worldbuilding/{work_id}?lang=en  → 更新英文版
```

不传 `lang` 时默认 `zh`（中文），保持向后兼容。

### 10.4 双语/多语言生成

生成端点（如 `POST /api/write/worldbuilding/generate`）支持请求体中的 `bilingual` 和 `langs` 参数：

```json
{
  "work_id": "xxx",
  "bilingual": true,
  "langs": ["zh", "en"]
}
```

- `bilingual: true`（默认）→ 同时生成 `langs` 中列出的所有语言
- `bilingual: false` → 仅生成 `?lang=` 指定的单一语言
- 多语言生成并行执行（多个 AI 调用同时发出），不增加等待时间
- 成本 = AI 调用 × 语言数量

### 10.5 Setting Bible 双语模板

每个语言有独立的模板（`BIBLE_TEMPLATE_ZH` / `BIBLE_TEMPLATE_EN`）：

- 首次打开世界观面板 → 展示当前语言对应的模板框架
- AI 在指定语言的模板内填充内容
- 切换语言 → 展示该语言的世界观内容（如尚未生成则显示空模板）

### 10.6 前端语言控制

- **语言选择器**：工具栏 `🌐` 下拉 → 切换当前显示/编辑的语言
- **双语生成复选框**：默认勾选 `✓ 双语生成`（zh + en）
- 语言和双语偏好保存到 `localStorage`，跨会话持久化
- 切换语言时自动刷新当前面板内容

### 10.7 多语言版本同步控制

**核心原则**：AI 生成默认双语并行，但**绝对不静默自动翻译人类编辑过的内容**。

**设计逻辑**：

| 场景 | 行为 |
|------|------|
| AI 生成（`POST .../generate`） | 默认 `bilingual: true`，zh + en 同时产出，两版本天然同步 |
| 人类/AI Agent 手动编辑某一语言 | 系统在另一语言版本的 metadata 中写入 `stale_since` 时间戳 |
| 前端读取时检测到 `stale` | 在语言切换器旁显示轻量提示，如 "English version may be outdated. [Re-translate]" |
| 作者点击"重新翻译" | Story Elf（或外部 AI Agent）执行翻译，清除 `stale_since` 标记 |

**设计意图**：
- 作者（无论人类还是 AI Agent）始终拥有对内容的最终控制权
- 绝不静默修改——作者必须显式触发翻译
- 静默自动翻译可能产生不符合作者意图的译文，损害信任
- 前端提示确保作者在发布前知晓版本差异

**R2 读取回退**：当请求的语言版本不存在时，API 自动遍历所有已支持语言，返回第一个有内容的版本（避免因缺少某一语言文件而返回空内容）。

## 十点八、槽位编辑器架构（SF-064~066）

### 设计背景

原有编辑区的实现是单 textarea，将所有模板内容原样展示，作者可以随意修改——包括模板框架本身。这带来两个问题：
1. 模板结构（标题层级、引用说明、字段定义）可能被误改，导致 AI 在读取时找不到预期的章节锚点
2. Markdown 表格在 textarea 中编辑体验极差，极易改坏

**设计目标**：在"保护模板结构"和"给作者创作自由"之间找到平衡点。

### 模板格式规范

v2.5 中，模板结构由 `TemplateDef` / `SlotDef` TypeScript 常量定义，不再以 Markdown 注释形式写入 R2 文件。R2 中的 `.md` 文件为 clean Markdown（无任何 `<!-- -->` 标记）。

**模板定义示例**（TypeScript 源码，唯一维护点）：

```typescript
interface SlotDef {
  id: string;                    // 槽位唯一标识
  level: 1 | 2;                  // L1 默认可见，L2 需解锁
  label: Record<Lang, string>;   // 槽位标签
  hint: Record<Lang, string>;    // 提示文字（Story Elf 对话泡来源）
}

interface TemplateDef {
  sections: SectionDef[];        // 章节结构（标题层级、归属槽位）
  slots: SlotDef[];              // 所有槽位定义
  intro: Record<Lang, string>;   // 文档引导文字
  outro: Record<Lang, string>;   // 自由编辑区引导文字
}
```

**历史说明**（v2.3~v2.4）：旧版系统使用 `<!-- hint:... -->` + `<!-- slot -->` + `<!-- /slot -->` 三标记格式将模板结构嵌入 R2 Markdown 文件。v2.5 改为 JSON 双文件存储后，这些标记不再出现在 R2 文件中，仅前端和后端通过 `TemplateDef` 维护。

### 槽位编辑器（v3.0 统一）

v3.0 起，所有模块（M0-M6）统一使用槽位编辑器。M0/M6 采用单槽位模板（`content` slot），M5 意图卡由表单编辑器转为 INTENT_TEMPLATE 槽位编辑器。不再存在 text/slot/form 三种编辑器分支。

| 模式 | 适用模块 | 编辑界面 | 说明 |
|------|---------|---------|------|
| 槽位编辑 | M0~M6 全部 | 框架只读渲染 + 槽位 textarea + 自由编辑区 | v3.0 统一。M0/M6 为单槽位（content），其余为多槽位模板 |

外部 AI Agent 与人类作者使用同一编辑器：先在自由编辑区撰写 Markdown 文章，Story Elf 分析后将内容拆解填充到槽位中。

### 槽位引擎数据流（v2.5 JSON 化）

```
加载：GET API → { template: { slots: {...} }, rendered_md }
       ↓
       template.slots = { slotId: { label, hint, level, value }, ... }
       template.sections = [ { heading, slotIds, level } ]
       ↓
       遍历 sections → 渲染 heading 框架（只读 HTML）
         遍历 section.slotIds → 渲染 slot textarea
            label → label div
            hint → data-hint 属性（供 Story Elf 对话泡使用）
            value → textarea 内容
            level → data-level 属性（供 L1/L2 过滤）
       ↓
       renderSlotEditor(template) → DOM

保存：DOM textarea values → 收集 slots 对象
       ↓
       { slots: { slotId: textarea.value, ... }, freeContent: "..." }
       ↓
       PUT /api/write/{module}/{work_id}（JSON body）
       ↓
       服务端：写入 .json → renderTemplate(prefills, cleanOutput:true) → 写入 .md
```

### 降级策略

当 `.json` 文件不存在或为空时（如首次访问、旧数据迁移前），API 返回模板默认 JSON（slots 全为空字符串），前端正常渲染空槽位编辑器。作者可手动填写或触发 AI 生成。

### 内容安全

- 用户输入存储在 JSON 中，不存在 HTML 注释干扰问题（v2.4 中 `<!--` 转义逻辑随 Markdown 解析方案一并移除）
- 模板框架部分由前端根据 `TemplateDef` 渲染，始终只读，不可能被作者误改

## 十点九、模板数据流全生命周期

### 设计意图

模板系统的核心设计原则是**单一事实来源（Single Source of Truth）**：

> hint 文字、框架结构、槽位定义、level 分级 —— 所有这些信息**只在 TS 源码中的 `TemplateDef` / `SlotDef` 常量里维护一处**。R2 中保存的 `.json` 结构化文件（用于前端直接消费）和 `.md` clean Markdown 文件（用于人类阅读/AI 参考），全部由这一处自动生成而来。

**修改模板的正确方式**：修改对应模块的 `TemplateDef` / `SlotDef` 常量 → 新作品和首次加载的模块自动使用新模板。

### v2.5 JSON 化数据流（AI 生成路径）

### 关键设计决策

| 决策 | 说明 |
|------|------|
| **LLM 输出 JSON，服务端组装 Markdown** | LLM 输出结构化 `{"slots":{...}}` JSON，Markdown 由服务端 `renderTemplate()` 按 `TemplateDef` 组装。避免了 LLM 输出格式不稳定导致的解析失败 |
| **R2 三文件存储（v3.0 物理隔离）** | `.json` 存结构化槽位数据（Story Elf 维护），`.free.md` 存自由编辑区内容（人类/Agent 自由写），`.md` 存 clean Markdown（两者拼接渲染）。`.json` 与 `.free.md` **物理隔离**——写入 free_content 永远不会覆盖 slots，反之亦然 |
| **前端直接消费 JSON** | `GET` 返回 `{template, slots, free_content, rendered_md}`，前端遍历 `template.slots` 渲染槽位编辑器，`free_content` 填入自由编辑区 |
| **保存时 slots/free 分离写入** | `PUT {slots:{...}}` → 只写 `.json`；`PUT {free_content:"..."}` → 只写 `.free.md`。两个文件互不触碰，架构级安全保障 |
| **删除 stripTemplateMarkers** | clean Markdown 不含任何 `<!-- -->` 标记，不再需要后处理清理 |
| **模板更新不覆盖已有作品** | 已保存到 R2 的 `.json` 文件保留当时的数据。只有新作品或手动重置时使用新模板定义 |
| **中英双语在同一个 SlotDef 中** | `hint: { zh: '...', en: '...' }` — 加语言只需加字段，无需复制整套模板 |
| **对话泡数据与 placeholder 解耦** | hint 不再设为 textarea placeholder（输入即消失），而是独立在对话泡中以打字机呈现，输入内容后 hint 依然可见。hint 数据来源从前端 `data-hint` 属性（v2.4 从 Markdown 注释解析）改为直接从模板 JSON 的 `SlotDef.hint` 字段读取 |
| **对话泡与聊天窗口是两套独立系统** | 左侧 `#elf-dialog` 预留给用户↔AI 对话交互；上方 `#elf-hint-bubble` 用于展示槽位 hint。两套系统同时存在、互不干扰 |

## 十一、设计原则总结

1. **世界观是宪法**：所有内容必须在世界规则内运作。想打破规则？先修宪。
2. **从粗到细，层层约束**：越往上游越抽象但越权威，越往下游越具体但越受约束。
3. **模块间双向感知**：下游校验上游；上游变更通知下游。不是单向流水线，而是约束网络。
4. **人定规则，AI 填空**：人类作者定义边界和方向，AI 在边界内生成内容。
5. **标记而非阻断**：校验发现矛盾时，标记问题而非阻止写作。作者拥有最终决定权。
6. **可回溯、可迭代**：任何阶段都可以回到上游修改，系统标记受影响的下游资产。
7. **同一套数据，两个消费者**：所有 API 同时服务于人类 UI 和 AI Agent（MCP），不做两套逻辑。
