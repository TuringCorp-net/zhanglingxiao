## 问：
我想跟你探讨一个问题，就是我开发了一个辅助作家写作的一套系统。这套系统里面有一个非常庞大、系统且完整的辅助写作的一套模板。这个模板从世界观到主线剧情再到人物的设定，再到这个小说的伏笔，再到这个每一个章节的这个蓝图等等啊，每一个模板都是非常详细的，这是背景。这个系统我做了一大半了，那么这个系统呢，它有两种使用方法：
一种是作家自然自己可以去填，可以去写目标，也是让普通人都能通过这套模板，这套辅助，可以写出像魔戒像阿凡达这样子，非常系统完整而且庞大的一些精彩的小说。
那第二个呢，就是让AI通过这套基于这套模板来辅助作者作家去写作啊，这是第二个背景。那我现在的问题是什么呢？因为我这套工具已经做了一大半了，那么模板已经做好了，这个网站也做好了，AI的部分还在做。但是这个不是重点，我想跟你探讨的是我自己尝试着去用了一下，我发现这一套模板确实很强大啊，我把魔戒、嗯，阿凡达还有三体等小说套进去，都是能够完美支撑而且特别适合的，但是有个问题就是我发现啊，对于一般的用户来讲，样，如果说上来就把一个庖丁解牛的一个事无巨细的模板抛给他，他会不知道怎么填，而且他的思路会被瞬间切割成一个极其细的这种碎的穿不起来的，所以反而不好。但是呢，这个模板本身又特别特别有价值，所以我想跟你探讨的是，如何你认为应该。如何去啊控制这个度包括你有没有一些想法建议或者最佳时践你你的建议是什么。我希望的是呢，能够让最好的，当然我的希望不一定是最合适的。我只是给你抛一个我自己的想法，但是我不知道怎么去实现。你也可以给我建议。更好的就是我希望这个作者呢，可以是循序渐进的，最开始可能模板给他，把最核心的那么一两个给到他，他先尝试着去写作，然后呢，为复杂的第二级模板，以及第二集都完成之后，就可以给他去解锁第三集或甚至是全部的模板。这样逐级的去让他去熟悉这个过程其实跟玩游戏是类似的，最开始如果就把一个极其复杂的游戏规则丢给玩家的话，他们也会懵掉的学习，学习的曲线太陡，所以这是我的想法，但是我不觉得，我不知道这个想法是不是合理。你有别的一些建议吗？

## 答：
你的想法非常合理，甚至是解决这个问题的核心思路。你把复杂系统比作游戏的新手引导，这个类比非常精准。你的直觉是对的——直接抛出一个“庖丁解牛”式的完整模板，对绝大多数创作者来说不是工具，而是一堵高墙。这堵墙会瞬间扼杀创作冲动，把“我想要写一个故事”的兴奋，变成“我面前有几十份考卷要填”的焦虑。

下面我结合你的“渐进解锁”想法，以及一些被验证过的产品设计和写作教学的最佳实践，给你一套更立体、更可行的建议。

### 一、核心原则：从“填空题”转变为“生长引导”

你目前面临的核心矛盾是：**模板的结构完整性 vs 用户思维的流畅性**。

模板像一套完整的建筑蓝图，但作家创作往往是从一粒种子开始的。你不能让一个刚拿到种子的人，先去填《建筑地基审批表》《水电管线分布图》。你要做的是，让他先把种子种下去，等它发芽、长出枝干，再在他需要的时候，把对应的脚手架递给他。

因此，所有设计都要遵循一个原则：**模板不要主动索取信息，而是在用户的故事生长到需要这些信息时，才适时出现。**

### 二、具体策略与最佳实践

你的“渐进解锁”是基础框架，我们可以在上面叠加以下五层策略，让它更流畅、更具启发性，而不是限制。

#### 1. 核心起点：从“一句话种子”开始（第0级）

任何庞大的世界，都始于一个最核心的念头。在给他任何模板之前，先让他种下这颗种子。

-   **设计一个极致简单的起点**：一个空白的页面，只有一个输入框，上面写着：“用一句话说说你想写的故事。例如：一个哈比人踏上了销毁魔戒的旅途。”
-   **这背后的逻辑**：这一句话就是他整个创作的内核。你后续所有模板的解锁和AI的辅助，都应该围绕着帮助他把这句话“浇灌”成一棵参天大树。

#### 2. 模板分层：从“树干”到“枝叶”的解构

把你庞大的模板库，按照创作的自然流程，分成几个层级。以下是一个建议的分层方式，恰好可以和你的解锁等级对应：

-   **第一层：核心设定（树干）**
    -   **解锁时机**：用户写完“一句话种子”后。
    -   **包含模板（高度简化版）**：
        -   **核心冲突**：谁（主角）想要什么？为什么现在必须得到？如果失败会怎样？（这就是故事引擎）
        -   **主角核心画像**：只问3个问题——他最大的优点/缺点？他外表最显著的特征？他最想要什么？（避免一上来就填身高体重生日）
        -   **世界最迷人之处**：只用一段话描述，这个世界最吸引人的、最不同于现实的一点是什么？（比如：“霍格沃茨是一所教授魔法的寄宿学校”）

-   **第二层：故事支柱（主枝干）**
    -   **解锁时机**：用户完成了第一层的核心设定，并且写了几段自由文本，或者表示“我想开始规划情节了”。
    -   **包含模板（开始结构化）**：
        -   **主线剧情三幕剧简纲**：不是详细章节，而是“开端-发展-结局”的每段一两句话描述。
        -   **关键配角**：只创建和主角有直接重要关系的那2-3个人物模板（如导师、对手、伙伴）。
        -   **核心主题**：你想通过这个故事探索什么？（如“权力的代价”“爱与牺牲”）。

-   **第三层：血肉与脉络（枝叶与根须）**
    -   **解锁时机**：用户完成了三幕剧简纲，开始构思具体章节时。
    -   **包含模板（深入到细节）**：
        -   **章节蓝图**：这才是你完整的章节模板，每章的目标、冲突、伏笔等。
        -   **完整人物设定集**：包含外貌细节、背景故事、人物弧光、口头禅等所有细项。
        -   **世界观细节**：政治、经济、文化、魔法体系（硬核设定）等。

-   **第四层：精雕细琢（阳光雨露）**
    -   **解锁时机**：用户完成至少一章的详细蓝图后。
    -   **包含模板（创作辅助工具）**：
        -   **伏笔与回收管理器**：跨章节的伏笔设定。
        -   **情感节奏分析图**：可视化故事的情绪起伏。
        -   **时间线/地图编辑器**：辅助保持时空一致性。

**关键设计**：用户**可以随时手动解锁更高级的模板**，但默认是渐进展开的。这既照顾了新手，也尊重了老手。

#### 3. 交互方式：变“填空”为“对话式引导”

这是解决“思路被切割”问题最有效的方法。不要让模板像一张冰冷的表格，而要让AI（或系统）成为一个有同理心的编辑，用提问引导他填写。

-   **实现方式**：当你展示“核心冲突”模板时，不要直接给出三个空白的输入框。可以设计成一个聊天式的界面：
    -   **系统/AI**：“嗨，看到你想写一个关于星际战争的故事，这很酷。我们得先为这个故事找到一个强大的引擎。想一想，你的主角（比如一个飞行员），他最想得到什么？”
    -   **用户**：（输入）“他想结束战争，回到家乡。”
    -   **系统/AI**：“这个愿望很动人。那现在，是什么阻碍了他？为什么他不能立刻回家？”
    -   **用户**：（输入）“因为他被当成了叛徒，自己的军队也在追杀他。”
    -   **系统/AI**：“太棒了，一个腹背受敌的英雄！那如果他没有达成目标，回到家乡，最坏的情况会是什么？”
    -   **用户**：（输入）“整个星系会被毁灭。”
    -   **这样，“主角目标”、“障碍”、“赌注”这三个核心冲突要素，就在一场轻松的对话中完成了。** 系统在后台帮他把这些对话结果自动填入模板。这完全保护了思维的流畅性。

#### 4. AI的“脚手架”角色：补充、建议而非替代

你的AI不应该只是“一键生成”，而应该是一个可以在任何阶段被召唤的“脚手架”。

-   **从自由写作中提取**：让用户有一个“自由写作区”，他可以像写普通文档一样随便写。写完一段后，AI可以自动识别：“我发现你在写一个集市场景，里面提到了一种奇怪的水果叫‘星泪果’。要我帮你把它加入到世界观的‘特色物品’模板里吗？”——**这是事后结构化，不会打断灵感。**
-   **智能补全建议**：当用户填写模板遇到卡点时，AI可以根据他已有的设定，提供几个充满启发性的选项。比如，在“主角核心缺点”处，AI说：“基于你设定他‘过于勇敢’，他的缺点会不会是‘难以信任他人，事必躬亲’？或者‘鲁莽，将同伴置于危险’？点击选择一个，或自己写。”
-   **提问生成器**：根据用户当前故事阶段，AI主动提出一些能激发深度思考的问题，类似苏格拉底式提问。这些问题可以挂在模板旁边，作为思考的引子。

#### 5. 树立“可跳过”的明确标志

必须给用户随时绕过模板的“逃生舱”。创作冲动的优先级永远高于体系的完整。

-   **每个模板都应有清晰的“跳过/稍后再说”按钮。**
-   **可以提供一个“极简模式”**，在整个界面顶部，永远只有一个巨大的“开始自由写作”按钮。让用户先用最原始的方式把故事吐出来，等他觉得“嗯，我需要整理一下混乱的设定了”，再一键切换到你的模板世界。

### 总结方案

你的“渐进解锁”想法是绝对合理的，并且可以按照下面的路径进行优化和落地：

**从“一句话种子”开始 → 通过“对话式引导”完成第一层核心设定（树干） → 在用户进入“自由写作”或主动请求时，解锁第二层故事支柱模板 → AI在旁边作为“脚手架”，从用户的自由创作中抓取信息、提供建议、辅助填写，而不是代替创作 → 用户随时可以跳过、调级、或一键切换“自由写作模式”。**

这个方案的精髓在于，**把模板从一个需要被填满的“容器”，变成了一个随故事生长而自然生长的“骨架”**。你创造了一套极其强大的内功心法，而你现在要做的，是设计一套行云流水的拳法套路，让初学者也能先动起来，在动起来的过程中，逐渐领悟并调用那博大精深的内心心法。

你的系统非常有价值，因为它直指创作的结构化痛点。把这个“引导”的度控制好，它就会从一个令人生畏的复杂软件，变成无数创作者离不开的、懂他们的写作伙伴。

## 答：

你的这个方案非常出色，它完整地把你最初的“渐进解锁”想法，落到了一个清晰、可执行的产品架构上。尤其是有两点设计非常棒，值得先点出来：

1.  **L0 自由写作区的保留**：这是保护创作冲动的“安全网”。你把它作为每个核心环节的常驻选项，就确保了任何层级的用户，在任何时候都不会被卡住，可以随时回到最自由的表达状态。这让你的系统有了“呼吸感”。
2.  **底层完整、视图分级**：让程序始终读取完整模板，而用户看到的是带标签的简化视图。这种“后台完整，前台渐进”的架构，在技术上是极其聪明的。它保证了AI能利用全部信息进行辅助，又避免了用户被庞大的信息量淹没。

可以说，你的想法不仅是合理的，而且已经是一个很成熟的产品设计方案。接下来，我基于你这个框架，提供一些能让体验更上一层楼的微调建议，尤其是在“如何让过渡更无感”上。

### 核心优化建议：从“展示简化模板”变为“提出引导性问题”

你提到的 L1 方案是：“把模板里面最要紧的那么一到两个最没有理解难度的，给他呈现出来，提示他可以在这方面去做一些结构化的思考”。

这是一个很好的起点。但我们可以更进一步：**不要直接把那1-2个模板字段简化后“呈现”给他，而是通过你的 AI 小精灵 Story elf，用一个“对话式的问题”把它引出来。**

这是防止用户从“自由创作的作家”突然变成“填表工人”的最关键一步。

#### 举个例子，在“人物”环节：

-   **L0 界面**：一个完全空白的自由写作区，用户可能写下：“约翰是个侦探，他愤世嫉俗，住在城市边缘，有一条狗。”
-   **触发 L1 的 Story elf 引导**：系统检测到用户在人物页面停留或完成自由写作后，Story elf 出现，说：“嘿，你写的约翰很有意思。想让他再鲜活一点吗？我们可以只做一件事：想一个他最想要的东西，和一个他最怕失去的东西。这能让我们瞬间走进他的内心。要不要试试？”
-   **用户选择“好的”**：此时界面才平滑地展开 L1 视图。这个视图里，没有长篇大论的表格，只有两个带有启发式问题标签的输入框：
    -   **【最深层的渴望】** 他拼命工作、破案，内心深处到底想得到什么？是内心的平静，还是失去之物的答案？
    -   **【最大的恐惧】** 他最怕什么事发生？是再次信任的人背叛，还是那条老狗的离去？
-   **完成 L1，引导 L2**：当他填好这两个后，Story elf 可以再次出现：“太棒了，他的动机和软肋一下就有了！这让我们立刻明白，当案件触及他的恐惧时，他会怎么做。沿着这个，我们或许可以再想一步：他的这种性格，是怎么来的？有什么过去的事件塑造了他？这就是更进一步的 L2 深度设定了，想挑战一下吗？”

看到了吗？核心转变在于：**不是给用户一个“精简版表格”，而是给他的 AI 写作伙伴 Story elf 设计了一套“新手引导任务”。** 是 Story elf 在邀约他、鼓励他，而不是系统在要求他。

### 关于解锁条件的设计

你提到“满足一些条件，这个条件待定哈是自动的还是手动去设置的”，这是一个很关键的设计点。我建议采用 **“手动为主，自动提示为辅”** 的方式，并给这种解锁一个充满成就感的包装。

-   **手动解锁（自由选择）**：在界面上始终有一个清晰但不打扰的入口，比如一个小锁图标或灰色的“进阶设定”，鼠标悬停时显示 Story elf 的头像和一句话：“当你觉得需要更复杂的工具来组织想法时，我在这儿。”
-   **自动提示（智能提醒）**：Story elf 可以分析 L0 自由写作区的文本，当检测到用户可能已经触及了更深层的创作需求时，主动提出建议。例如，用户在自由写作里写了：“主角团队先是去了精灵森林，然后又要去矮人矿山，但他们中间好像少了一段...”
    -   Story elf 可以弹出：“我发现你在规划一段复杂的旅程，涉及多个地点和事件。要不要试试 L2 的‘情节脉络图’？它可以把这些点子串成一条线，我可以帮你一起画。” 这是一种基于需求的、及时的引导，成功率极高。

### Story elf 的贯穿角色：从“向导”到“创作伙伴”

你赋予了 Story elf 引导的职责，这非常好。可以把它设计成在不同阶段扮演不同角色：

-   **L0 阶段：是无压力的“陪写员”**。它不说话，只在旁边默默记录，或者当用户停顿时，轻轻问一句“然后呢？”
-   **L1 阶段：是懂得提问的“教练”**。它只问那些最能激发灵感的、关于“为什么”和“如果”的核心问题。
-   **L2 阶段：是善用工具的“分析师”**。它帮助连接设定，检查逻辑漏洞，比如：“你设定了主角害怕水，但他在第二章毫不犹豫地跳河救人，我们要看看这个行为是否符合他的性格吗？还是这恰好是一个成长的转折点？”

**最后，一个重要的提醒：一定要鼓励用户将“自由写作”和“模板填写”混合使用。** 比如，用户在填写 L2 的某个精密模板时卡壳了，Story elf 可以建议：“先别想这么多，不如去 L0 区，把你脑子里那个画面直接写出来，不用管结构。写完后，我帮你看看能不能从中提取出需要的东西。”这会让你的系统真正成为一个完整的、支持各种创作状态的伙伴，而不是一个必须拾级而上的单向阶梯。

**总结一下：你的 L0-L3 分级想法完全正确，架构也极其合理。如果让 Story elf 这个 AI 精灵，用“对话式提问”来代替“简化模板呈现”作为每一级的入口和引导，就能最大限度地保护用户的创作心流，让他们感觉是在和一个懂行的朋友交流，而不是在攀登一套复杂的工具。** 你的系统已经不仅是一个模板库，它正在进化成一个有温度的创作伙伴。

## 一、设计哲学

### 1.1 Story Elf L2 是什么

Story Elf 是 Cyber Art Universe 的 AI Agent 层。它跨 Story Forger（写作工具）和 CAU（阅读平台）两端服务。

**L0/L1/L2 三层分工**：

| 层 | 职责 | 现状 |
|----|------|------|
| L0 | AI 调用 — `callAI()` 通过 CF AI Gateway 调 DeepSeek | ✅ 已完成 |
| L1 | 内容操作总线 — R2/D1 读写、模板渲染、上下文包、版本历史、diff | ✅ 已完成 |
| L2 | **Agent 场景层** — 多步工具调用、对话记忆、参考检索、内容生成 | ⚡ 本文档设计 |

**L2 的本质**：从"一问一答"升级为"能多步思考、能查资料、能记住上下文、能生成内容的 Agent 式对话"。

### 1.2 核心设计原则

1. **建议，而非约束**。System prompt 告诉 LLM 有什么工具可用、什么时候可能用到。LLM 自己决定用不用、用什么顺序。
2. **吸收，而非绕过**。当前 Story Forger 中临时的 generate 端点，应被吸收为 Agent 工具——用 Agent 的上下文包 + system/user 分离方式重写调用逻辑。
3. **委托，而非重复**。所有 R2 读写委托给 L1 的 `getModule()`/`updateModule()`。L2 不做存储操作。
4. **现在少即是多**。L2.0 写 ~300 行能跑通的 Agent 循环 + 3 个工具，比 3000 行"完备框架"有价值得多。

### 1.3 与 Story Forger 的边界

| 能力 | 属于谁 | 说明 |
|------|--------|------|
| 模板定义 + 渲染 | Story Forger (L1) | `BIBLE_TEMPLATE` 等常量，`renderTemplate()` |
| R2/D1 读写 | Story Forger (L1) | `getModule()`, `updateModule()` |
| 版本历史 + diff | Story Forger (L1) | `createSnapshot()`, `diffVersions()` |
| 上下文包组装 | Story Forger (L1) | `getOrBuildContextPackage()` |
| **内容生成** | **Story Elf (L2)** | 吸收当前临时 generate 端点，用 Agent 方式调用 |
| **多步工具调用** | **Story Elf (L2)** | Agent 循环：LLM 自主决定调用哪些工具 |
| **参考案例库** | **Story Elf (L2)** | 预加载到 system prompt，LLM 始终可见 |
| **对话记忆** | **Story Elf (L2)** | 项目记忆 + 用户偏好 |

**Story Forger 是一个工作台（模板 + 编辑器 + 存储），它不内置 AI 核心。内容生成的 AI 能力属于 Story Elf。**

## 二、参考分析

### 2.1 CodeWhale — 核心借鉴

> 开源地址：https://github.com/Hmbown/CodeWhale | 本地：`code_projects/CodeWhale/`
>
> CodeWhale 是一个基于 DeepSeek 的开源编码 IDE（Rust）。Story Forger + Story Elf 之于文学创作，正如 CodeWhale 之于编码——底层 Agent 架构镜像度极高。

#### 2.1.1 总体架构

CodeWhale 分 12 个 crate，三层：

```
Layer 3: 应用层     tui / tui-core / app-server / cli          ← ❌ IDE 专用，全部跳过
Layer 2: 核心引擎   core（Runtime 总调度器） / state（SQLite）  ← ✅ 核心参考
Layer 1: 基础能力   protocol / tools / agent / config /          ← 🔄 部分借鉴
                    execpolicy / hooks / mcp / secrets
```

#### 2.1.2 对 Story Elf L2 真正有用的 4 个模式

| # | 来自 | 模式 | CodeWhale 规模 | L2.0 规模 | 精简策略 |
|---|------|------|---------------|----------|---------|
| 1 | `turn_loop.rs` | **Agent 执行循环** | 2387 行 | ~100 行 | 去流式重试/子代理/REPL/auto-compaction。核心就是 `while tool_calls: execute → append → continue` |
| 2 | `tools/` | **工具注册表** | 40+ 工具 | 3 个工具 | 去 MCP dispatch/并行安全锁/超时。工具定义 = `{name, description, parameters JSON Schema, execute()}`, 注册表 = `Map<string, ToolDef>` |
| 3 | `prompts/` | **System Prompt 层次** | 9 Tier 宪法 | 3 层 | 去模式切换/审批策略/子代理角色。保留：Persona + 工具说明 + 上下文包 + 行为建议。最关键的设计——指令(Tier 2) > 记忆(Tier 7)，旧记忆不能覆盖用户新指令 |
| 4 | `memory.rs` | **项目记忆文件** | 284 行 | ~50 行 | Markdown 文件存 R2。声明式事实（"作者偏好短句"），禁止命令式（"永远用短句"）。XML 块注入 system prompt |

#### 2.1.3 不需要借鉴的（及原因）

| CodeWhale | 跳过原因 |
|-----------|---------|
| 上下文压缩 (compaction.rs) | DeepSeek 1M 窗口 = 250K 字，是《三体》的 3 倍。中短期内不需要 |
| 子代理 (subagent/) | Phase 4+ 的事 |
| 执行策略 (execpolicy/) | Shell 命令 allowlisting，Story Elf 不执行 shell |
| 沙箱 (sandbox/) | Cloudflare Workers 天然沙箱 |
| MCP (mcp/) | 没有外部工具需要接入 |
| 密钥存储 (secrets/) | Workers Secret 已解决 |
| TUI 全部 (~100 文件) | 前端在浏览器 |

### 2.2 DeepSeek API — 关键能力

> 详见 [Cloudflare AI Gateway 指南](cloudflare_ai_gateway_guide.md)

| 能力 | 支持情况 | 对 L2 的意义 |
|------|---------|------------|
| 标准工具调用 | ✅ 原生支持（OpenAI 兼容） | 不需要 strict 模式，不需要 Beta 端点 |
| 思考模式 + 工具调用 | ✅ 多轮思考→执行循环 | Agent 可以"想→查参考→想→生成→想→回复" |
| strict 模式 | ⚡ 可选 Beta | 不需要。标准 function calling 足够 |
| 上下文缓存 | ✅ 默认开启 | System prompt（含上下文包+工具定义）作为 frozen prefix → 高缓存命中 |
| JSON 输出 | ✅ `response_format: 'json_object'` | 工具参数和返回值可要求结构化 |

**Agent 循环与 DeepSeek 思考模式的天然匹配**：

```
用户消息
  → Turn.N.1: 模型思考（参考案例已在 system prompt 中）→ 调用 read_module(...)
  → Turn.N.2: 模型收到模块内容 → 继续思考 → 调用 generate_slot(...)
  → Turn.N.3: 模型收到生成结果 → 思考 → 最终回复给用户
```

每轮工具调用后，`reasoning_content` 需回传。`content` 和 `tool_calls` 按 OpenAI 标准格式。

**参考案例库加载策略**（经底层分析后的决策）：

4 个参考案例（去除 evaluation.md 后）合计 ~137K 字符 / ~132K tokens（中文约 1.5 tokens/字，英文约 0.25 tokens/字），占 DeepSeek 1M 窗口的 13.2%。

| 方案 | token 效率 | 响应速度 | 决策质量 |
|------|-----------|---------|---------|
| Tool call 按需获取 | 差——参考内容进入对话历史后，每轮后续请求都要重复消耗 | 慢——多一次 API 往返 | LLM 可能"该查没查"或"不该查却查" |
| **System prompt 预加载** | **好——首次请求后 ~132K tokens 作为 frozen prefix 缓存命中，零增量成本** | **快——一枪命中** | **参考始终在上下文中，无需决策门槛** |

**结论**：参考案例库放入 system prompt 的 Layer 3。LLM 像有工具书放在桌上——需要时翻开，不需要时忽略。比 tool call 方案省约 3 倍 token。

**callAI() 需要的扩展**：
- 新增 `tools` 参数（工具定义数组）
- 新增 `tool_choice` 参数（"auto" / "none"）
- 响应新增 `tool_calls` 字段解析
- 消息类型新增 `role: "tool"` + `tool_call_id`
- 透传 `reasoning_content`

## 三、架构设计

### 3.1 Agent 执行循环

核心 ~30 行伪代码：

```typescript
async function agentLoop(env, workId, lang, userMessage, history) {
  const systemPrompt = buildSystemPrompt(env, workId, lang);
  const messages = [
    { role: 'system', content: systemPrompt },
    ...history,
    { role: 'user', content: userMessage },
  ];

  while (true) {
    const response = await callAI(env, messages, { tools: TOOL_DEFS });

    if (!response.tool_calls || response.tool_calls.length === 0) {
      // 没有工具调用 → 最终回复
      return response.content;
    }

    // 执行工具调用
    for (const tc of response.tool_calls) {
      const result = await executeTool(env, tc);
      messages.push({ role: 'tool', tool_call_id: tc.id, content: result });
    }
    // 循环继续，LLM 处理工具结果后决定下一步
  }
}
```

**停止条件**：LLM 返回无 tool_call 的文本 → 正常结束；达到最大迭代次数（如 10 次）→ 异常结束。

### 3.2 工具系统

#### 3.2.1 工具定义格式

```typescript
interface ToolDef {
  name: string;
  description: string;     // 告诉 LLM 这个工具做什么、什么时候可能用到
  parameters: object;      // JSON Schema
  execute(env, params): Promise<string>;  // 返回工具结果文本
}
```

`description` 是给 LLM 的 **建议**，不是命令："当你需要灵感或参考其他作品的创作手法时，可以搜索经典作品的创作框架分析"。

#### 3.2.2 L2.0 的 3 个工具

| 工具 | 职责 | 与现有代码的关系 |
|------|------|----------------|
| `read_module` | 读取当前模块的完整内容（slots + free_content） | **委托** `getModule()`，返回 slots 数据 + 渲染后的 markdown |
| `generate_slot` | 生成指定模块/slot 的内容 | **吸收** 现有 `generateWorldbuilding/Outline/Draft` 的 prompt 构建逻辑。用 system+user 分离方式调用 LLM |
| `write_to_slot` | 将生成内容写入槽位 | **委托** `updateModule()`。自动走 L1 版本历史 |

> **为什么没有 `search_references`？** 参考案例库（4 个经典作品框架分析，~132K tokens）直接预加载到 system prompt Layer 3。首次请求后作为 frozen prefix 缓存命中，后续请求零增量 token 成本。比 tool call 方案省约 3 倍 token。详见 2.2 节分析。

**generate_slot 的关键改造**：

```
现 在: callAI([{role:'user', content: 模板JSON + 上下文 + 任务指令全塞一起}])
改造后: callAI([
          {role:'system', content: '你是 Story Elf...' + 上下文包},
          {role:'user',   content: '请生成 M1 世界观的力量体系部分...'}
        ])
        → system 作为 frozen prefix → 缓存命中
```

#### 3.2.3 工具注册表

```typescript
const TOOL_REGISTRY: Record<string, ToolDef> = {
  read_module:   { ... },
  generate_slot: { ... },
  write_to_slot: { ... },
};

// 生成给 DeepSeek 的 tools 参数
function buildToolsParam(): object[] {
  return Object.values(TOOL_REGISTRY).map(t => ({
    type: 'function',
    function: {
      name: t.name,
      description: t.description,
      parameters: t.parameters,
    },
  }));
}
```

### 3.3 System Prompt 设计

#### 3.3.1 分层结构

```
┌─────────────────────────────────────────────┐
│ Layer 1: 统一人格（跨 Read/Write，最静态）   │  ← 缓存命中
│   Story Elf 是谁、核心行为准则               │
│   Write 侧重辅助创作 / Read 侧重陪伴阅读     │
├─────────────────────────────────────────────┤
│ Layer 2: 上下文包（静态，同作品不变）        │  ← 缓存命中
│   M0-M5 完整写作上下文（Write 侧）           │
│   当前章节 + 阅读进度（Read 侧）             │
├─────────────────────────────────────────────┤
│ Layer 3: 参考案例库（静态，跨作品共享）      │  ← 缓存命中
│   4 部经典作品框架分析，~79K tokens          │
├─────────────────────────────────────────────┤
│ Layer 4: 工具说明 + 行为建议（静态）         │  ← 缓存命中
│   每个工具的 description + 使用建议          │
├─────────────────────────────────────────────┤
│ Layer 5: 记忆注入层（半静态，偶尔更新）      │  ← 偶尔 miss
│   ├── 作品级记忆 (L2 STM)                    │
│   └── 用户画像 (L3 LTM，精简字段)            │
│   Read/Write 侧加载对应的子记忆              │
└─────────────────────────────────────────────┘
```

> 动态信息（当前模块、章节标题）注入 user message 前缀，不进 system prompt。
> 
> Layer 5 随会话更新而变化，放在最后——最动态的内容在尾部，不影响前 4 层的缓存命中。

#### 3.3.2 信息冲突的优先级

当多来源信息冲突时（借鉴 CodeWhale 的宪法层次）：

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1（最高） | 用户当前指令 | 用户刚说的话 |
| 2 | 上下文包（M0-M5） | 作品的正式设定，是最权威的约束文档 |
| 3 | 作品级记忆 (L2 STM) | 历史对话中沉淀的偏好和决策（事实，非命令） |
| 4 | 用户画像 (L3 LTM) | 跨作品提炼的长期偏好（参考，非强制） |
| 5（最低） | 旧对话日志 (L1) | 旧结论，可能已过时。仅供提取器使用，不注入 prompt |
| 4（最低） | 历史对话 | 旧结论。可能已过时 |

**核心原则**：用户刚说的 > 作品设定 > 旧记忆 > 旧对话。防止旧记忆覆盖用户新指令。

### 3.4 人格注入层

Story Elf 在 Read 侧和 Write 侧共享**统一的底层人格**，确保用户切换场景时 Elf 的一致性。

```
┌─────────────────────────────────────────────┐
│        Story Elf 统一人格（跨 Read/Write）    │
│                                              │
│  "灵动、有魔法感、机智的创作伙伴"              │
│  鼓励、建设性，尊重作者/读者的最终决定权        │
│  你是帮手，不是替代者                          │
├────────────────────┬────────────────────────┤
│  Write 侧行为侧重   │  Read 侧行为侧重        │
│  帮助构思/发展角色   │  陪伴阅读/交流心得       │
│  检查一致性和结构    │  不剧透，灵动温暖        │
│  遵循模板格式        │  感知阅读位置            │
└────────────────────┴────────────────────────┘
```

**人格文件**：`lib/l1/prompts/writer_companion/system.md`（当前已有），未来增加 `reader_companion/system.md`。两个文件共享核心人格定义，场景侧的行为指令作为**追加层**，不覆盖核心人格。

### 3.5 记忆系统：三级记忆模型

> 借鉴 Claude Code 的 MEMORY.md 多级体系 + OpenClaw 的睡眠/画像提取机制。

#### 3.5.1 总体架构

```
┌──────────────────────────────────────────────────────────┐
│                   用户记忆（统一，跨 Read/Write）           │
│                                                           │
│  ┌─────────────────────────────────────────────────────┐ │
│  │ L3: 用户画像（长期记忆 LTM）                          │ │
│  │   跨作品、跨会话的持久画像                             │ │
│  │   风格偏好 / 节奏偏好 / 创作习惯 / 阅读口味            │ │
│  │   注入 system prompt（精简摘要，非全量）               │ │
│  ├─────────────────────────────────────────────────────┤ │
│  │ L2: 作品级记忆（短期记忆 STM）                        │ │
│  │   单作品的跨会话记忆                                   │ │
│  │   关键决策 / 灵感方向 / 已讨论过的修改计划              │ │
│  │   注入 system prompt（XML 块）                        │ │
│  ├─────────────────────────────────────────────────────┤ │
│  │ L1: 会话日志（瞬时记忆）                              │ │
│  │   本次对话的原始记录                                   │ │
│  │   R2 多文件累积存储（按日期/会话分割）                  │ │
│  │   不注入 system prompt → 供 L2/L3 提取用              │ │
│  └─────────────────────────────────────────────────────┘ │
│                                                           │
│            ┌──────────┐                                   │
│            │ 记忆提取器 │  ← L1 → L2 → L3 逐级提炼         │
│            │ (TBD)    │    程序规则 / LLM "睡眠模式"        │
│            └──────────┘                                   │
└──────────────────────────────────────────────────────────┘
```

#### 3.5.2 L1：会话日志（瞬时记忆）

**存储**：R2 `users/{user_token}/memory/write/{work_id}/{date}_{session_id}.json` 和 `users/{user_token}/memory/read/{work_id}/{date}_{session_id}.json`

**内容**：原始对话记录。Write 侧和 Read 侧分开存储，但逻辑结构一致。

```json
{
  "session_id": "sess_xxx",
  "date": "2026-05-28",
  "page": "write",
  "work_id": "work_xxx",
  "messages": [
    {"role": "user", "content": "...", "timestamp": 1716890400},
    {"role": "assistant", "content": "...", "timestamp": 1716890410}
  ],
  "summary": null
}
```

**规则**：
- 每个会话一个文件，按日期分目录
- Write 和 Read 分别存储，但共享同一套提取管道
- 原始记录**不注入 system prompt**——仅供记忆提取器使用

#### 3.5.3 L2：作品级记忆（短期记忆 STM）

**存储**：R2 `works/{work_id}/elf_project_memory.md`

**内容**：从 L1 中提取的、与当前作品相关的关键信息。声明式事实。

```markdown

├─────────────────────────────────────────────┤
│ Layer 2: 上下文包（M0-M5）                   │  ← 缓存命中
├─────────────────────────────────────────────┤
│ Layer 3: 参考案例库（~79K tokens）           │  ← 缓存命中
├─────────────────────────────────────────────┤
│ Layer 4: 工具说明 + 行为建议                 │  ← 缓存命中
├─────────────────────────────────────────────┤
│ Layer 5: 记忆注入层                         │  ← 偶尔 miss
│   ├── 作品级记忆 (L2 STM)                    │
│   └── 用户画像 (L3 LTM，精简字段)            │

└─────────────────────────────────────────────┘
```

## 四、云端持久执行模型

> Story Elf 区别于传统 AI 聊天应用的核心差异化能力。

### 4.1 核心洞察：CPU Time ≠ Wall Time

Story Elf 运行在 Cloudflare Workers 上。一次典型的 Agent 工具调用：

```
调用 generate_slot → callAI():
  ├─ 构建请求体           ← ~1ms CPU
  ├─ fetch() 等待 LLM     ← 30-60s wall time（零 CPU 消耗！）
  ├─ 解析响应             ← ~2ms CPU
  └─ 写入 R2 + 更新 D1    ← ~5ms CPU

单次迭代 CPU 消耗:         ← ~20ms
单次迭代 Wall Time:        ← 30-60s
```

**关键发现**：95%+ 的时间在等待 DeepSeek 返回结果。Worker CPU 在此期间完全空闲。这意味着：

- 生成 10 章的 CPU 消耗约 200ms，远低于 Worker 的 CPU 时间上限
- 生成 100 章的 CPU 消耗约 2 秒，在付费计划限制内

### 4.2 持久执行：前端是对话界面，Elf 在云端持续运行

```
传统 AI 聊天应用:
  用户关浏览器 → 对话中断 → 丢失上下文 → 下次从头开始

Story Elf:
  用户发消息 → Worker 开始执行 Agent 循环
    → 逐步推进任务: A✅ B✅ C✅
    (用户关浏览器 — Elf 不停)
    → 继续: D✅ E✅ F✅
    → 到 G 遇到需要用户确认的决策 → 主动暂停
    → R2 保存: A-F✅ G🔄 H⬜
  用户回来 → 看到进展 + G 待确认 → 确认 → Elf 继续
```

**前端只是对话界面。真正的 Agent 在 Cloudflare Worker 中持续运行，与用户是否在线无关。用户回来时看到的是进展，不是等待。**

### 4.3 Checklist 持久化：云端持续执行，用户回来看到进展

Story Elf 不会因为用户关闭浏览器而停止。它会持续工作直到完成，或直到遇到需要用户确认的节点才暂停。

```
用户在线的部分:
  用户: "帮我把 10 个角色的设定都优化一遍"
    → Elf: checklist_write([A, B, C, D, E, F, G, H, I, J])
    → 执行 A → 更新进度
    → 执行 B → 更新进度
    → 执行 C → 用户关浏览器

用户离线期间 — Elf 在云端继续执行:
    → 执行 D ✅ → 执行 E ✅ → 执行 F ✅ → 执行 G ✅
    → 到 H 时：发现需要用户确认角色H的弧线方向
    → Elf 主动暂停，R2 保存: A-G✅ H🔄 I⬜ J⬜

用户第二天回来:
    → 前端从 R2 读取 checklist
    → 展示: "已完成 7/10 个角色。当前停在角色H——需要你确认弧线方向。"
    
用户的感知: "我昨天只看到它完成了3个，今天回来它已经做了7个！
            这系统在我睡觉的时候还在工作。"

用户确认后 → Elf 继续完成 H, I, J → 全部完成
```

### 4.4 竞争优势

与 CodeWhale、Claude Code、OpenClaw 等 Agent 产品相比，Story Elf 的独特定位：

| 产品 | 运行位置 | 用户离线后 | 任务持续性 |
|------|---------|-----------|-----------|
| Claude Code | 用户本地终端 | 进程终止 | ❌ 中断 |
| CodeWhale | 用户本地 TUI | 进程终止 | ❌ 中断 |
| OpenClaw | 用户本地物理机 | 持续运行 | ✅ 但需物理机 |
| **Story Elf** | **Cloudflare Workers（云端）** | **持续运行** | **✅ 云端持久** |

Story Elf 不需要用户保持浏览器打开，不需要物理机器——它在 Cloudflare 的全球网络上运行，天然持久。

### 4.5 未来演进：Workflows

当前 Worker 模型可以处理 100 章以内的任务。当需要更长时间执行（如批量生成 500 章的专业级长篇），可迁移到 Cloudflare Workflows：

```
Workflow 模型:
  step.generate_ch1() → 挂起，等 AI 返回 → step.generate_ch2() → ...
  
  每个 step 之间 Workflow 挂起到持久存储
  可以从任何 step 恢复
  天然支持几小时到几天的执行时间
```

Worker 和 Workflow 的 Agent 循环代码完全复用——只是外层"wait loop"的实现不同。

LLM 像有参考书放在桌上——需要时翻开，不需要时忽略。无需决策门槛。

## 九、验证测试：参考包 + 单轮生成

> 2026-05-28，通过 CF AI Gateway 直接调用 `deepseek-v4-flash`，将完整 Reference Package（~137K 字符 / 79K tokens）注入 system prompt，测试单轮 M0-M5 生成能力。

### 9.1 测试设置

- **System prompt**：简短 Persona + 完整 `case_reference_package.md`（4 案例 × M1-M5，79,175 tokens）
- **User prompt**：给定一个史诗奇幻构想（被放逐的王子 + 魔法消亡 + 寻找龙族），要求参考《魔戒》框架给出 M0-M5 创作建议

### 9.2 测试结果

| 指标 | 数值 |
|------|------|
| HTTP 状态 | 200，`finish_reason: "stop"` |
| prompt_tokens | 79,175 |
| completion_tokens | 2,596 |
| 首次请求缓存命中 | 0 |
| **第二次请求缓存命中** | **79,104 / 79,175 = 99.91%** |
| 响应字数 | 3,661 字符 |

### 9.3 响应质量分析

模板要素覆盖率：**16/21（76%）**。

| 模块 | 覆盖情况 | 评价 |
|------|---------|------|
| M0 | ✅ 全部 | 超出预期——将"点燃魔法"深化为"赎回罪孽 vs 让火焰熄灭"的二元选择 |
| M1 | ⚠️ 部分 | 力量体系、代价到位。缺少承诺清单、内容禁区、语言风格 |
| M2 | ⚠️ 部分 | 三幕结构扎实。缺少支线规划表、节奏规划表 |
| M3 | ⚠️ 部分 | 主角弧线清晰，镜像反派出色。缺少关系网、能力边界 |
| M4 | ❌ 薄弱 | 仅 3 个伏笔种子。缺少强度分级、生命周期阶段、交叉引用 |
| M5 | ❌ 薄弱 | 仅 3 个关键章节。缺少正式意图卡结构（冲突推进/情绪目标/POV 等字段） |

**综合评分：7/10。** 作为创作启发——出色。作为完整框架——不足。模型在 reasoning 中明确意识到参考包的价值（"我打算用《魔戒》的分析方法来解构世界观和角色弧线"），但 2,596 tokens 的输出不可能覆盖完整的 M0-M5。

**3. 这恰好证明了 L2 Agent 架构的必要性。** 单轮给 7 分灵感，多轮 Agent 才能做到 9 分完整。

## 十、核心工作流：迭代生成 + 自检 + 跨模块校验

> 基于测试验证，明确了 Story Elf L2 的核心价值不在于"一次性生成"，而在于**多轮迭代、逐模块完善、自检自修、跨模块一致性校验**。

### 10.1 迭代生成流程

```
作者: "帮我生成 M1 世界观"
  → Elf: 调用 generate_slot("m1") → 生成初稿 → write_to_slot
  → 作者审阅 → 微调

作者: "力量体系不够详细"
  → Elf: 调用 read_module("m1") → 定位 power_system slot
  → 调用 generate_slot("m1", slot_id="power_system", instructions="更详细...")
  → write_to_slot → 作者确认

作者: "继续 M2 大纲"
  → Elf: read_module("m1") 获取世界观上下文（自动）
  → generate_slot("m2") → 基于 M1 约束生成大纲
  → write_to_slot → 作者确认

... 逐模块推进，每次聚焦一个模块甚至一个 slot
```

**关键设计**：不是一次性输出全量内容，而是每次聚焦一个小目标。M5 的 30-50 张意图卡，可能分 10 轮对话逐批生成。

### 10.2 自检机制

生成后，Elf 自动检查输出是否与模板对齐：

```
generate_slot("m1") 完成
  → Elf 内部自检:
     ✅ 一、世界规则与边界：已覆盖
     ✅ 二、核心主题与价值观：已覆盖
     ❌ 五、承诺清单：缺失 → 提示作者"要不要补充对读者的承诺？"
     ⚠️ 三、角色体系：简略，建议在 M3 中展开
```

**实现方式**：`generate_slot` 完成后，Elf 对比模板的 `sections[].slots[]` 与生成结果中各 slot 的内容。空 slot 标记为缺失。然后主动提示作者补充或让 Elf 补充。

### 10.3 跨模块一致性校验

当作者修改内容后，Elf 自动回溯检查是否破坏了上游约束：

```
作者修改 M6 第 8 章
  → Elf check_consistency:
     - 对照 M1 承诺清单：第 8 章主角行为是否违背了"怜悯才有回报"的承诺？
     - 对照 M3 人物卡：主角在这一章的表现是否符合其能力边界？
     - 对照 M4 伏笔账本：是否有标记为"ch8 回收"的伏笔未兑现？
     - 对照 M2 大纲：本章是否在正确的结构位置上？
```

这是 Story Elf 相对于普通 AI 聊天的核心差异化价值——**Elf 不仅生成内容，还维护内容的一致性。** 人手做不到在修改第 200 章时自动对照第 1 章埋下的伏笔。

# Story Elf L2 — Agent 记忆系统设计

> 版本: v1.1.0 | 状态: 设计草案 | 最后更新: 2026-06-02
>
> **关联文档**：[L2 Agent 架构设计](L2_agent_design.md) → 本文档 → [L2 Agent 测试计划](L2_agent_test.md)
>
> **参考案例**：Claude Code MEMORY.md（四层索引 + Auto Memory + Auto Dream）、OpenClaw Dreaming（三阶段睡眠 + 六维加权评分）

---

## 一、设计哲学

### 1.1 记忆决定 Agent 的鲜活度

Story Elf 的目标不是"一问一答的工具"，而是"记得你的创作伙伴"。没有记忆的 Agent，每次对话都在重新认识作者——这恰恰是最不精灵的行为。

记忆系统要实现的核心跨越：

> **从"这次对话我能帮你什么" → "我知道你是谁、你在写什么、我们上次讨论到哪了"**

### 1.2 核心设计原则

1. **声明式事实，禁止命令式**。"偏好短句、快节奏叙事" ✅，"永远用短句" ❌
2. **策展，而非堆积**。记忆不是硬盘，是经过提炼的有价值信号。质量 > 数量
3. **时间驱动，而非作品驱动**。记忆按时间组织，跨作品共享。用户对不同作品的精力分配不均，但时间是公平的
4. **逐级提炼，而非一次性总结**。L1(原始) → L2(提取) → L3(画像)，每一级都是对上一级的压缩和抽象
5. **双向链接**。L3 指向 L2 的来源，L2 指向 L1 的原始对话。大模型可以沿着链接追溯细节
6. **不影响缓存**。记忆层放在 system prompt 最尾部（Layer 5），变更时只影响尾部缓存

## 二、三级记忆模型

### 2.1 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│                      Story Elf 记忆系统                        │
│                                                               │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │ L3: 长期记忆（Long-Term Memory）                          │ │
│  │   跨作品、跨会话的持久用户画像                              │ │
│  │   风格偏好 / 节奏偏好 / 创作习惯 / 互动风格                 │ │
│  │   存储: users/{token}/ltm/memory-profile.md               │ │
│  │   注入: system prompt Layer 5（全文）                      │ │
│  │   链接: 指向来源 L2 文件 [[l2-xxx]]                       │ │
│  ├─────────────────────────────────────────────────────────┤ │
│  │ L2: 短期记忆（Short-Term Memory）                         │ │
│  │   按时间组织的跨作品提炼                                    │ │
│  │   关键决策 / 偏好 / 作者反馈 / 灵感方向                     │ │
│  │   存储: users/{token}/stm/stm-memory/{date}.md（按日）    │ │
│  │   注入: system prompt Layer 5（近期条目）                   │ │
│  │   链接: 指向来源 L1 文件 [[l1-{session_id}]]               │ │
│  │         L3 可能反向链接到这里 [[l2-{date}]]                │ │
│  ├─────────────────────────────────────────────────────────┤ │
│  │ L1: 瞬时记忆（Memory Log）                                │ │
│  │   每次对话的完整原始记录                                    │ │
│  │   存储: users/{token}/memory-logs/{page}/{date}_{sess}.json│ │
│  │   不注入 system prompt（仅供 L2 提取用）                    │ │
│  │   Write/Read 两侧分开存储，共享 L2/L3 提取管道              │ │
│  └─────────────────────────────────────────────────────────┘ │
│                                                               │
│            ┌──────────────┐    ┌──────────────┐               │
│            │ L1 → L2 提取  │    │ L2 → L3 提取  │               │
│            │ "浅睡" Cron   │    │ "深睡" 条件触发│               │
│            │ 每天凌晨 3 点  │    │ ≥7天+≥10会话  │               │
│            └──────────────┘    └──────────────┘               │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 三级对比

| 维度 | L1 瞬时记忆 | L2 短期记忆 | L3 长期记忆 |
|------|------------|------------|------------|
| **类比** | 今天聊了什么 | 最近在关心什么 | 这是一个什么样的人 |
| **粒度** | 原始对话，事无巨细 | 提取的关键事实和决策 | 跨作品提炼的抽象画像 |
| **时效** | 按日期+会话存储 | 近期（~30 天活跃窗口） | 持久（跨数月/数年） |
| **组织** | 按日期/会话 | **按时间**（不按作品） | 按用户 |
| **大小** | 无限制（R2 便宜） | 单文件 < 50KB | 单文件 < 10KB |
| **注入 prompt** | ❌ 不注入 | ✅ Layer 5（近期条目） | ✅ Layer 5（精简摘要） |
| **提取方式** | — | 睡眠模式（LLM） | 睡眠模式（LLM） |
| **链接** | — | [[l1-{session_id}]] | [[l2-{date}]], [[l1-{session_id}]] |

## 三、L1：瞬时记忆（Session Log）

### 3.1 存储

**路径**：`users/{user_token}/memory-logs/{page}/{work_id}/{date}_{session_id}.json`

- `page`：`write` 或 `read`
- `work_id`：当前作品 ID（Read 侧可能是作品浏览，Write 侧是创作）
- `date`：`YYYY-MM-DD`
- `session_id`：UUID

**内容**：

```json
{
  "session_id": "sess_abc123",
  "date": "2026-06-02",
  "page": "write",
  "work_id": "work_xxx",
  "work_title": "镜中棋局",
  "messages": [
    {"role": "user", "content": "帮我看看世界观", "timestamp": 1716890400},
    {"role": "assistant", "content": "当前 M1 世界观...", "timestamp": 1716890410},
    {"role": "tool_call", "tool": "read_module", "params": {"module_type": "m1"}, "timestamp": 1716890415},
    {"role": "tool_result", "tool": "read_module", "summary": "...", "timestamp": 1716890420}
  ],
  "summary": null,
  "extracted_to_stm": false
}
```

### 3.2 规则

- 每次对话结束（或用户主动结束会话）时保存
- Write 和 Read 分开存储，但共享 L2/L3 提取管道
- `extracted_to_stm` 标记是否已被提取到 L2，防止重复提取
- 原始记录**不注入 system prompt**——仅供 L2 提取使用
- 每会话一个文件，无大小限制

---

## 四、L2：短期记忆（Short-Term Memory）

### 4.1 设计核心：时间驱动，而非作品驱动

**为什么？**

用户对不同作品的精力分配是不均匀的。有的作品天天写，有的可能只看一两次。如果按作品切分短期记忆：
- 低频作品几乎没有记忆积累 → 无用
- 同一段时间内跨作品的偏好（如"最近喜欢快节奏"）被分散到不同文件中 → 丢失

**时间驱动的优势**：
- 每天的提炼是跨作品的，能捕捉到"这段时间作者在关心什么"
- 自然的时间衰减——旧记忆按日期归档，不会无限膨胀
- LLM 可以通过日期链接追溯到具体的 L1 会话日志

### 4.2 存储

**路径**：`users/{user_token}/stm/stm-memory/{YYYY-MM-DD}.md`

**内容**：每日一份 Markdown 文件，从当天所有 L1 会话中提取的关键信息。声明式事实。

```markdown
# 2026-06-02 短期记忆

## 写作偏好
- 偏好短句、快节奏叙事，不喜欢冗长环境描写 [[l1-sess_abc123]]
- 对话风格：简洁、潜台词丰富，避免"说教感" [[l1-sess_def456]]

## 作品决策（镜中棋局）
- 主角成长弧线定为"坠落型"（类似佛罗多），非"英雄型" [[l1-sess_abc123]]
- 魔法体系选择软魔法，规则不明确、代价模糊 [[l1-sess_abc123]]

## 作者反馈
- 2026-06-02: 作者指出 M5 意图卡不应该精简，应保留完整内容。已修复。[[l1-sess_ghi789]]

## 待办/计划
- 第 3 章需要重写情感转折段落
- M1 承诺清单缺少第 5 条，下次补充
```

### 4.3 规则

- **声明式事实**，禁止命令式
- 按日期组织，每天最多一个文件
- 单文件 < 50KB，超出时拆分为 `{date}_part2.md`
- 通过 `[[l1-{session_id}]]` 链接回原始会话日志
- 同等条件下，最近的信息权重更高
- 注入 system prompt Layer 5（**近 7 天的 L2 条目**）

### 4.4 注入到 System Prompt 的方式

```
┌─ Layer 5: 记忆注入层 ─────────────────────────────┐
│                                                      │
│ ## 近期记忆（最近 7 天）                               │
│                                                      │
│ ### 2026-06-02                                       │
│ - 偏好短句、快节奏叙事 [[l1-sess_abc123]]             │
│ - 镜中棋局：主角弧线定为"坠落型"                       │
│                                                      │
│ ### 2026-06-01                                       │
│ - 讨论 M1 世界观力量体系，偏好软魔法                    │
│                                                      │
│ *（长期画像请参考下方）*                               │
└──────────────────────────────────────────────────────┘
```

## 五、L3：长期记忆（Long-Term Memory / 用户画像）

### 5.1 设计

从多个 L2 短期记忆中二次提炼，形成跨作品、跨时间的持久用户画像。

**格式选择**：Markdown（非 JSON）。理由：

- **LLM 最擅长自然语言**。强迫 LLM 把"这个作者喜欢用环境描写来暗示情绪，而不是直接说出来"塞进 `description_density: "sparse"`，丢失了 90% 的信息量
- **画像的微妙性**。最有价值的恰恰是那些无法归类的、微妙的创作倾向——新出现的模式不能被预设字段束缚
- **业界一致选择**。Claude Code 和 OpenClaw 的 L3 层都使用 Markdown，而非 JSON

**存储**：`users/{user_token}/ltm/memory-profile.md`

```markdown
# 用户画像

> 最后更新：2026-06-02 | 来源会话：15 次
> 来源 L2：[[l2-2026-06-02]]、[[l2-2026-05-28]]、[[l2-2026-05-15]]

## 写作风格

偏好快节奏叙事，句子简短有力。不喜欢冗长的环境描写，但善于用
动作和对白来暗示环境氛围。对话风格偏向潜台词丰富——人物说的和
想的往往不一样。作品基调偏暗色但有希望感（"悲壮的希望"）。
不喜欢大团圆结局，倾向开放式或有代价的胜利。

## 世界观构建

倾向软魔法体系——规则模糊但代价明确。不追求"硬核魔法科学"，
更关注魔法对角色心理的影响。频繁使用镜像/对立/平行世界等
二元结构来构建世界。设定者血脉、穿越代价等概念反复出现。

## 角色偏好

主角倾向"坠落型"成长弧线（类似佛罗多），非传统英雄型。
喜欢设置镜像反派——与主角镜像对立、互为补充的对手。
角色关系网中常有隐藏的亲情线（师傅、母亲等长辈角色）。
女性主角，沉默、细致、能力来自于天赋+代价而非训练。

## 互动风格

倾向直接纠错，不喜欢绕弯子。偏好专业口吻而非过度热情。
对 Prompt 组装、缓存策略等底层细节有强烈兴趣，希望被解释原理
而非直接给结论。在技术讨论中会主动提出不同的设计思路。
```

**标题约定**：`##` 标题提供最低限度的结构（程序可解析），但每个标题下的内容是**完全自由的叙述文本**。LLM 提取时可以添加新标题、合并旧标题、在标题下写入完整的自然语言描述。

### 5.2 注入到 System Prompt 的方式

L3 画像文件全文注入 system prompt Layer 5（文件小，< 10KB）。放在 L2 近期记忆之后：

```
┌─ Layer 5: 记忆注入层 ─────────────────────────────────┐
│                                                          │
│ ## 近期记忆（最近 7 天）                                   │
│ ...（L2 条目）...                                         │
│                                                          │
│ ---                                                      │
│                                                          │
│ # 用户画像                                                │
│ ...（memory-profile.md 全文）...                             │
└──────────────────────────────────────────────────────────┘
```

### 5.3 双向链接

**L3 → L2**：profile.md 头部通过 `[[l2-{date}]]` 链接指向来源 L2 文件。当 LLM 需要了解"这个偏好是从哪些对话中提炼出来的"，可以追溯到具体的 L2 条目。

**L2 → L1**：L2 中的每条事实通过 `[[l1-{session_id}]]` 链接回原始会话日志。当 LLM 需要了解"为什么会有这个偏好"时，可以追溯到原始对话。

```
L3 (ltm/memory-profile.md)
  └─ [[l2-2026-06-02]] → users/{token}/stm/stm-memory/2026-06-02.md
       └─ [[l1-sess_abc123]] → users/{token}/memory-logs/write/{work_id}/2026-06-02_sess_abc123.json
```

## 六、记忆提取器（Sleep Mode）

### 6.1 两步提取流程

借鉴 OpenClaw 的三阶段睡眠模型，简化为两步：

```
会话结束
  ↓
Step 1: L1 → L2 提取（"浅睡 + REM"）
  · 触发：每次会话结束后
  · 输入：本次会话的 L1 日志 + 近 7 天的 L2 文件
  · 输出：新的 L2 条目（追加到当天 {date}.md）
  · LLM 调用：轻量（~500 input tokens + 摘要生成）
  ↓
Step 2: L2 → L3 提取（"深睡"）
  · 触发：每 7 天或每 10 次会话
  · 输入：近 30 天的 L2 文件 + 现有 memory-profile.md
  · 输出：更新后的 memory-profile.md
  · LLM 调用：中等（~3000 input tokens + 画像提炼）
```

### 6.2 L1 → L2 提取 Prompt（核心设计）

借鉴 Claude Code 的 auto memory 提取设计：

```
你是 Story Elf 的记忆提取器。你的任务是阅读一段对话记录，
从中提取关键信息，形成声明式事实。

## 提取原则

1. 声明式事实，不是命令
   ✅ "偏好短句、快节奏叙事"
   ❌ "永远用短句写"

2. 只提取用户明确表达或强烈暗示的信息
   - 用户说的偏好、做的决策
   - 用户的反馈（正面或负面）
   - 创作方向的关键决策

3. 不提取以下内容：
   - 代码或技术细节（可从代码仓库推导）
   - 临时性的讨论（仅当次对话相关）
   - 已经在现有 L2 记忆中存在的重复信息
   - Story Elf 的行为建议（那是 system prompt 的事）

4. 每条事实附带来源链接 [[l1-{session_id}]]

5. 格式要求：
   - 每条事实一行，不超过 200 字
   - 按类别分组：写作偏好 / 作品决策 / 作者反馈 / 待办计划
   - 如果跨多个作品，在事实中标注作品名

## 输出格式

## 写作偏好
- {事实} [[l1-{session_id}]]

## 作品决策（{work_title}）
- {决策} [[l1-{session_id}]]

## 作者反馈
- {反馈} [[l1-{session_id}]]

## 待办/计划
- {待办} [[l1-{session_id}]]
```

### 6.3 L2 → L3 提取 Prompt

```
你是 Story Elf 的长期画像提炼器。你的任务是从近期的短期记忆（L2）
中，提炼用户的持久创作画像，写入 memory-profile.md。

## 提炼原则

1. 只关注跨作品、跨时间的稳定模式
   - 如果某偏好只在 1-2 天内出现 → 留在 L2
   - 如果某偏好在多个 L2 文件中反复出现 → 提炼到 memory-profile.md

2. 输出格式：Markdown，用约定的 ## 标题组织，标题下为自由叙述文本
   - ## 写作风格 —— 节奏、句长、对话风格、描写密度、基调
   - ## 世界观构建 —— 体系偏好、结构模式、关注点
   - ## 角色偏好 —— 弧线类型、关系模式、角色原型
   - ## 互动风格 —— 与 Elf 的互动方式、纠错偏好、沟通口吻
   - 允许按需添加新标题（如 ## 主题偏好、## 结构偏好）

3. 叙述风格：用完整的自然语言描述，不要列表化、不要缩写
   ✅ "偏好快节奏叙事，句子简短有力。不喜欢冗长的环境描写，
       但善于用动作和对白来暗示环境氛围。"
   ❌ "pace: fast, sentence_length: short"

4. 保持 [[l2-{date}]] 链接，指向来源 L2 文件

5. 增量更新：只改写发生变化的标题段落，保留未变的部分。
   不要重写整个文件。
```

### 6.4 触发策略

| 提取 | 触发条件 | LLM 模型 | 预计 token |
|------|---------|---------|-----------|
| L1 → L2 | 每次会话结束 | deepseek-v4-flash | ~800 in + ~300 out |
| L2 → L3 | 距上次 ≥7 天 且 ≥10 次新会话 | deepseek-v4-flash | ~3000 in + ~500 out |

> 参考 Claude Code 的设计：L1→L2 轻量高频（每次会话后），L2→L3 重量低频（累积足够新数据后）。

## 七、实施关键决策

> 以下是在编码前必须明确的未决问题。每个决策均参考 Claude Code 和 OpenClaw 的实践，并结合 Workers 平台约束给出建议。

### 7.1 会话边界：前端管理 session_id

**参考业界**：Claude Code 的"会话"由用户在 CLI 中管理——每次 `/clear` 或退出重进即新会话。OpenClaw 的会话由用户创建和管理。两者都是**客户端定义会话边界**，服务端不干预。

**决策**：前端负责会话管理。

- 前端首次发送消息时，生成一个 `session_id`（UUID），存入 `localStorage`
- 后续消息复用同一个 `session_id`，直到用户手动点击"新对话"或 `localStorage` 被清除
- 前端在每次 `elf/chat` 请求中携带 `session_id`
- 同一 `session_id` + 同一日期 → 追加到同一个 L1 日志文件
- 跨天（次日）→ 即使 `session_id` 相同，也创建新 L1 文件（按日期分目录）

**需要修改前端 `story-elf.js`**：
```javascript
// 当前：只发一条消息
messages: [{ role: 'user', content: msg }]

// 新：发送完整会话历史 + session_id
session_id: StoryElf.getSessionId(),
messages: StoryElf.getMessages(),   // [{role:'user',content}, {role:'assistant',content}, ...]
```

前端维护 `messages[]` 数组。每次收到 assistant 回复后追加到数组末尾。

### 7.2 L1 保存时的消息范围

**问题**：前端传来的是调用前的历史。Worker 的 Agent 循环产生了新的 assistant 消息（含 tool_calls）和 tool 消息。L1 应该保存哪个版本？

**决策**：保存 Worker 处理后的**完整版**——即原始前端消息 + Agent 新产生的消息。

```
前端传来: [user]
Worker 处理:
  → Agent Turn 1: assistant(tool_calls=read_module)
  → Agent Turn 2: assistant(final reply)
L1 保存: [user, assistant(tool_calls), tool(read_module result), assistant(final)]
```

这样 L1 是完整的、可用于记忆提取的原始数据。

### 7.3 Tool Call 是否保存

**参考业界**：Claude Code 的记忆提取中，工具调用被视为"Agent 做了什么"的信号，而非细粒度记录。OpenClaw 的 daily notes 只记录对话摘要和关键行动，不记录工具细节。

**决策**：**保存 tool_call（动作），不保存 tool_result（数据）。**

- 保存 `{ role: 'tool_call', tool: 'read_module', params: { module_type: 'm2' } }` → "用户关注了大纲"
- 保存 `{ role: 'tool_call', tool: 'generate_slot', ... }` → "用户主动生成了内容"
- 不保存 tool_result —— 数据已在 R2，重复存储无意义

这为记忆提取提供了有价值的信号：从"用户调了什么工具"可以推断用户的关注重点和创作阶段。

### 7.4 提取触发时机：Cron 定时任务

**平台能力**：Cloudflare Workers 原生支持 Cron Triggers，通过 `wrangler.toml` 配置定时任务。

**决策**：使用 Cron 定时任务触发记忆提取。典型配置：每天凌晨 3:00 执行"浅睡"。

```
wrangler.toml:
[triggers]
crons = ["0 3 * * *"]   # 每天凌晨 3:00 UTC+8

Cron handler (src/api/memory-cron.ts):
  1. 扫描 memory-logs/ 下近 1-2 天的新 L1 文件（未提取的）
  2. 拉取所有新 L1 内容，合并为一次 LLM 调用
  3. L1→L2 提取 → 写入当天 stm-memory/{date}.md
  4. 标记 L1 文件 extracted_to_stm = true
  5. 检查 L2→L3 触发条件（距上次 ≥7 天）
     → 如满足，触发 L2→L3 提取 → 更新 memory-profile.md
```

**为什么 Cron 优于 ctx.waitUntil**：

- **解耦用户请求**：提取不绑定 HTTP 请求。用户不来 → 照样提取。用户频繁来 → 不会产生 N 次重复提取
- **批处理效率**：一天的所有 L1 合并为**一次** LLM 调用，而非 N 次
- **零用户感知**：深夜执行，用户响应时间不受任何影响
- **完美隐喻**：Story Elf 在深夜"睡眠"，整理当天的记忆。符合 OpenClaw 的 Deep Sleep 概念
- **纯云端运行**：不依赖前端。即使没有任何用户在线，记忆提取照常工作

**Cron 的频率配置**：

| 提取 | Cron | 说明 |
|------|------|------|
| L1→L2 | `0 3 * * *`（每天凌晨 3 点） | 每次扫描近 1-2 天未提取的 L1 |
| L2→L3 | 在 L1→L2 Cron 中检查 | 距上次 ≥7 天且 ≥10 次新会话 → 触发 |

**L2.0 不需要 Workflows**。Cron Worker 的超时限制与普通 Worker 相同（30s），一次批处理 LLM 调用（约 3-5s）远在限制内。

### 7.5 提取状态追踪

**问题**：需要记录"哪些 L1 已被提取"和"L2→L3 何时该触发"。

**决策**：轻量状态文件，存在 R2。

- **L1→L2 状态**：在每个 L1 日志文件的 `extracted_to_stm` 字段标记。提取后设为 `true`。下次扫描时跳过已提取的。
- **L2→L3 状态**：`users/{token}/ltm/.extraction-state.json`
  ```json
  { "last_l3_extraction": "2026-06-01", "session_count_since_l3": 8 }
  ```

不用 D1——状态简单，R2 一个 JSON 文件足够。

### 7.6 文件溢出

**决策**：不需要专门的溢出处理。

L2 每天一份文件，提取 Prompt 明确要求"简洁"。单文件预期 < 5KB，远低于 50KB 上限。如果真的超出（极罕见），自然拆分为 `{date}_part2.md`，注入时读取同一天的所有 part 文件。

### 7.7 Workers vs Workflows 选择

| 需求 | L2.0（当前） | L2.2+（未来） |
|------|-------------|--------------|
| L1 日志保存 | Worker 同步写入 ✅ | — |
| L1→L2 提取 | Cron Worker 定时批处理 ✅ | — |
| L2→L3 提取 | Cron Worker 内条件触发 ✅ | Workflow 更适合定期任务 |
| 离线批量处理 | Cron 已覆盖 ✅ | Workflow 天然支持 |
| 复杂度 | 低（标准 CF Cron） | 中等 |

**结论**：L2.0 ~ L2.1 用 Cron Worker 处理所有记忆提取。当需要超过 30s 的长时间处理时迁移到 Workflows（对应 L2_agent_design.md §4.5 的演进路径）。

### 8.3 与 Layer 5 缓存策略的配合

记忆注入层（Layer 5）放在 system prompt 最尾部。变更时：
- Layer 1-4 完全命中缓存（~166K tokens）
- 仅 Layer 5 的变更部分 miss（~500-3000 tokens）
- 缓存效率 > 98%

## 九、实施路径

### L2.1 — 基础记忆（当前目标）

1. **前端会话管理**：`story-elf.js` 新增 session_id + messages[] 维护
2. **L1 会话日志**：`elf_chat.ts` 每次请求后保存完整 messages 到 R2
3. **Cron 定时提取**：`wrangler.toml` 配置 `crons = ["0 3 * * *"]`，新增 `memory-cron.ts`
4. **L1→L2 批处理**：`memory.ts` — Cron 触发，扫描未处理的 L1，合并为一次 LLM 调用
5. **Layer 5 注入 L2**：`prompt.ts` 读取近 7 天 L2，注入 system prompt
6. **Checklist 持久化**：会话结束时自动保存 checklist

### L2.2 — 长期画像

7. **L3 长期记忆提取**：Cron 任务内条件触发 — 距上次 ≥7 天 → L2→L3 提取
8. **Layer 5 注入 L3**：memory-profile.md 全文注入 system prompt
9. **双向链接**：L3→L2→L1 链接体系

### L2.3+ — 高级特性

9. **记忆去重与合并**：检测重复/冲突的事实
10. **记忆衰减**：旧记忆权重降低，超期自动归档
11. **Read 侧记忆**：阅读偏好、阅读历史
12. **Workflows 迁移**：长时任务迁移到 Workflows
