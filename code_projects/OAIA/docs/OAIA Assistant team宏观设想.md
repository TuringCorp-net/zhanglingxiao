 # 多层次用户交互式 Agent Team 架构方案

 ## 1. 设计目标

把“自然交互”前移到终端，把“深度求解”后移到云端。

这不是简单的算力分工，而是：
	•	交互职责 与 求解职责 的分离
	•	低延迟人格层 与 高能力任务层 的分离
	•	持续陪伴 与 按需重算 的分离

这一步非常关键。


传统单层 Agent 的主要问题是：
	•	首 token 延迟明显
	•	用户输入后需等待主模型完整思考
	•	长任务会阻塞前台交互
	•	用户中途修正意图时，系统响应不自然
	•	streaming 只是“过程展示”，不等于真正协作

因此，本方案的目标是构建一个：

前台持续交互、后台持续求解、调度层持续判断
的多层次 Agent Team 系统。

其核心价值不在于单次回答“更长”，而在于：
	•	更强的实时交互感
	•	更低的首反馈延迟
	•	更自然的中途修正能力
	•	更接近人与人协作的对话体验
	•	更适合复杂任务、长任务与动态任务

⸻

 ## 2. 核心设计思想

本架构不是“一个 Agent 干到底”，而是把系统拆成三个不同时间尺度、不同职责边界的智能层：

第一层：前台交互层

负责与用户进行极低延迟的实时互动。

第二层：中台调度层

负责基于当前会话草稿与状态，进行任务判断、切换、取消、继续、发布结果等调度决策。

第三层：后台执行层

负责真正的重任务求解、工具调用、长推理、子 Agent 协作。

⸻

 ## 3. 总体架构

用户
  ↕
前台交互层 Front Agent
  ↕
会话草稿 / 状态层 Conversation Draft
  ↕
中台调度层 Supervisor Agent
  ↕
任务快照 / 任务控制层 Task Snapshot + Task Control
  ↕
后台执行层 Worker Agent / Agent Team
  ↕
结果流 Result Stream
  ↕
前台交互层拼接反馈
  ↕
用户

 ## 4. 各层职责定义

4.1 前台交互层（Front Agent）

定位

一个超低延迟、轻量级、持续在线的会话代理。

主要职责
	1.	接收用户输入
	2.	维护会话草稿本（Conversation Draft）
	3.	记录用户新增、修正、撤回、替换的信息
	4.	给用户提供低成本 ACK 式反馈
	5.	读取结果流中的新结果
	6.	将后台结果与当前会话做轻量自然拼接后反馈给用户

不负责的事情

前台层不负责：
	•	正式总结用户需求
	•	抢答或提前给最终答案
	•	发起复杂任务分解
	•	做深推理
	•	调用重工具链
	•	决定 kill / patch / restart 任务

输出风格

前台层的反馈应控制在：
	•	收到
	•	已更新
	•	明白
	•	按你刚才的新说法记下了
	•	后台已按最新条件更新处理中

它的本质是：

交互存在感维持器 + 会话速记器
而不是答案生成器。

⸻

4.2 会话草稿层（Conversation Draft）

定位

前台与中台之间的共享状态缓冲区。

作用

用于承载用户当前意图的持续演化过程，而不是一次性任务输入。

核心特点
	1.	动态更新
	2.	可撤销
	3.	允许用户边说边改
	4.	不直接作为后台执行输入
	5.	仅作为中台生成任务快照的原始依据

可包含内容

ConversationDraft
- latest_user_input
- current_intent_notes
- added_constraints
- revoked_constraints
- unresolved_points
- recent_corrections
- current_dialogue_context
- latest_result_pointer


⸻

4.3 中台调度层（Supervisor Agent）

定位

整个系统的智能控制面。

主要职责
	1.	周期性读取 Conversation Draft
	2.	判断当前意图是否已形成稳定可执行任务
	3.	生成新的 Task Snapshot
	4.	判断现有任务是否应：
	•	继续
	•	修补
	•	取消
	•	替换
	•	新建
	5.	决定后台结果是否可发布到 Result Stream
	6.	维护任务生命周期与状态流转

特征
	•	频率低于前台层
	•	智力高于前台层
	•	主要依赖模型语义判断，而非大量硬编码规则
	•	但动作空间受系统边界约束

核心思想

调度层不是传统规则引擎，而是：

LLM Supervisor Policy

即：
让模型判断“当前应采取哪种控制动作”，
但动作集合是有限且受控的。

推荐动作空间

NO_OP
WAIT
START_NEW_TASK
PATCH_CURRENT_TASK
CANCEL_AND_RESTART
PUBLISH_PARTIAL_RESULT
PUBLISH_FINAL_RESULT
IGNORE_CHANGE


⸻

4.4 任务快照层（Task Snapshot）

定位

中台从动态草稿中提炼出的稳定执行版本。

作用

后台执行层不直接读取不断变化的草稿本，而是执行某一时刻冻结下来的任务快照。

目的
	1.	保证执行对象稳定
	2.	保证取消与替换逻辑清晰
	3.	保证结果可追溯
	4.	避免后台在执行时被前台频繁扰动

可包含字段

TaskSnapshot
- snapshot_id
- created_at
- source_draft_version
- user_goal
- confirmed_constraints
- output_requirements
- unresolved_ambiguities
- supersedes_snapshot_id
- supervisor_rationale


⸻

4.5 后台执行层（Worker Agent / Agent Team）

定位

真正干活的执行面。

主要职责
	1.	按 Task Snapshot 执行任务
	2.	进行长推理、深分析、多步工具调用
	3.	必要时唤起子 Agent Team 协作
	4.	输出中间结果或最终结果
	5.	接受中台调度层的：
	•	cancel
	•	replace
	•	patch
	•	continue
指令

特点
	•	可用更强模型
	•	可配合工具链
	•	可异步运行
	•	允许比前台和中台更高延迟
	•	专注于结果质量，不承担用户实时对话职责

⸻

4.6 结果流层（Result Stream）

定位

后台结果向前台回传的版本化结果缓冲区。

作用

前台不直接消费“裸执行结果”，而是读取结果流中的结构化产物。

必要性

如果只有一个单槽 result，会导致：
	•	旧结果被新结果覆盖
	•	前台无法判断哪条结果对应哪版任务
	•	用户看到的内容容易跳变
	•	难以区分阶段结果与最终结果

推荐结构

ResultItem
- result_id
- snapshot_id
- task_id
- status: draft | partial | final | canceled
- content
- confidence
- created_at
- superseded_by


⸻

 ## 5. 系统运行机制

5.1 用户输入阶段

用户连续输入、补充、修改、撤回自己的表达。

前台交互层实时做两件事：
	1.	轻量 ACK，与用户保持自然交互感
	2.	持续维护 Conversation Draft

⸻

5.2 调度判断阶段

中台调度层以固定节拍运行，例如每 1–3 秒一次。
必要时也可由关键事件触发额外检查。

它读取当前 Conversation Draft，并进行语义判断：
	•	当前是否已有可执行意图
	•	相比上一版任务是否发生了本质变化
	•	当前应等待、继续还是替换任务

⸻

5.3 快照生成阶段

当调度层判断当前意图已具备执行价值时：
	•	生成新的 Task Snapshot
	•	决定是否取消旧任务
	•	决定是否新开后台 Worker

⸻

5.4 后台执行阶段

后台执行层依据 Task Snapshot 运行：
	•	重推理
	•	工具调用
	•	搜索
	•	子任务协作
	•	多 Agent 分工

并将阶段结果写入 Result Stream。

⸻

5.5 前台拼接反馈阶段

当前台检测到 Result Stream 中有可发布结果时：
	•	读取对应 ResultItem
	•	做轻量 surface-level 拼接
	•	将结果以自然、不突兀的方式反馈给用户

这里前台只做：

表面表达拼接（surface realization）

不做：

语义再解释（semantic transformation）

⸻

 ## 6. 设计原则

原则一：前台克制

前台只负责实时交互感，不负责真正求解。

原则二：调度靠智能，不靠规则树

中台的 kill / patch / continue / restart 主要依赖模型判断，而不是大量手写 if/else。

原则三：系统边界仍然存在

虽然调度依赖 AI 语义判断，但以下内容必须由系统约束：
	•	调度节拍
	•	状态合法性
	•	任务 ID 与版本号
	•	资源上限
	•	任务取消机制
	•	日志与可观测性
	•	工具权限与安全边界

原则四：执行基于快照，不基于草稿本

后台执行对象必须是冻结后的 Task Snapshot，而不是持续变化的 Conversation Draft。

原则五：结果必须版本化

所有结果都必须可追踪到对应任务版本，避免前台展示混乱。

⸻

 ## 7. 与传统单层 Agent 的区别

传统单层 Agent
	•	单一模型主导
	•	用户输入后整体阻塞
	•	streaming 只是过程展示
	•	中途修正成本高
	•	长任务显著拖慢交互体验

本方案
	•	多时间尺度分层
	•	前台低延迟持续在线
	•	中台智能调度
	•	后台异步重任务执行
	•	用户可边说边改
	•	交互与求解解耦
	•	更接近真实协作过程

⸻

 ## 8. 方案价值

这个架构的主要价值不在于：
	•	单次回答一定更长
	•	单次推理一定更深
	•	最终答案必然比单模型更准

而在于：

真实价值
	1.	显著改善首反馈体感
	2.	提升复杂对话的连续性
	3.	支持用户中途修正目标
	4.	降低长任务对前台交互的阻塞
	5.	提升系统的协作感与在线感
	6.	为多 Agent、多工具、多任务并发打下清晰骨架

⸻

 ## 9. 一句话总结

这个架构本质上是：

用轻量前台维持实时交流，用智能中台做语义调度，用重量后台完成深度任务。

它不是把一个 Agent 做得更大，
而是把整个系统做成一个：

能够边交流、边判断、边执行、边反馈的多层次 Agent Team。

 ## 示例场景：前台自然交互 + 后台异步任务 + 结果无缝拼接

1. 场景目标

该场景用于说明多层交互式 Agent Team 架构在真实用户对话中的工作方式：
	•	前台助手始终低延迟在线
	•	轻量交互即时完成
	•	重任务在后台异步执行
	•	后台结果在合适时机自然融入对话
	•	用户不会感受到明显的“模式切换”或“等待阻塞”

该场景尤其适用于：
	•	智能眼镜
	•	陪伴式硬件
	•	桌面智能助理
	•	手机端 AI 助手
	•	语音优先的实时交互系统

⸻

2. 场景背景

用户正在通过一个持续在线的 AI 助手进行日常交流。
系统架构为：
	•	穿戴设备/输入设备：负责语音采集与播放
	•	本地主终端（手机 / PC / Mac）：运行前台交互层
	•	云端：运行中台调度与后台任务执行层

其中：
	•	前台层负责自然接话、轻量回应、短时状态维护
	•	后台层负责搜索、分析、规划、生成攻略等重任务
	•	前台与后台通过会话草稿和结果流进行协同

⸻

3. 典型对话示例

3.1 用户发起闲聊

用户：
“哎，助手啊，你好呀。”

前台助手立即回复：
“你好呀～今天状态怎么样？外面天气还挺舒服的，你这是准备认真上班，还是已经在偷偷想下午去哪儿玩了？” 😄

说明

这一轮属于纯前台即时交互：
	•	不需要云端重任务
	•	不需要长思考
	•	重点是低延迟、自然、风格化
	•	目的是让用户感受到助手“始终在线、随时可聊”

⸻

3.2 用户发起轻查询

用户：
“今天天气几度啊？”

前台助手立即承接：
“我看一下哈，很快～”

随后，系统快速完成天气查询。

前台助手在短时间后补充：
“查到了，今天大概 20 度，体感会比较舒服，下午出门的话挺合适的。”

说明

这一轮体现的是轻任务即时承接 + 快速补结果：
	•	前台先接住用户，避免沉默等待
	•	天气查询属于轻量任务，可以快速返回
	•	用户体验上是“像有人在边听边查”，而不是“发出请求后卡住几秒”

⸻

3.3 用户触发重任务

用户：
“那不错呀。不过我今天还得工作，但如果下午有空的话，你给我推荐几个可以去玩的地方吧。”

前台助手立即回复：
“好呀，这个我可以帮你想一版～我先按你今天下午有空这个情况给你整理一下。你这边更想轻松一点，还是稍微活动一下？还有，你今天工作会不会很累？”

说明

这一轮非常关键，它触发了后台异步重任务。

在这一刻，系统内部会发生两件事：

前台层做的事情
	•	立即承接任务，告诉用户“我开始帮你准备了”
	•	继续自然对话，不中断交流
	•	顺便补充收集偏好信息，例如：
	•	想轻松还是活动一下
	•	工作累不累
	•	是否在意预算
	•	是否希望离得近

后台层做的事情
	•	中台调度层识别出“下午游玩推荐”属于重任务
	•	创建任务快照
	•	启动后台 Worker：
	•	获取用户城市/位置上下文
	•	结合天气、时间段、出行半径
	•	搜索合适地点
	•	生成一版轻量攻略方案

这里的重点是：

后台已经开始工作，但前台对话完全不被阻塞。

⸻

3.4 前台继续陪聊，同时补充约束

用户：
“今天工作应该还好，但我不想太累，最好别太远。”

前台助手：
“明白了，那我先按‘轻松一点、不要太远’这个方向帮你想。这样的话，下午就不适合太折腾，最好是能放松一点、又不至于浪费天气。”

说明

这一轮体现的是前台继续维护会话草稿：
	•	用户新增了两个重要约束：
	•	不想太累
	•	不要太远
	•	前台及时吸收这些信息
	•	中台可以据此更新或修补后台任务

这说明前台并不只是“陪聊”，而是在持续为后台任务补充可用信息。

⸻

3.5 后台结果生成完成

经过几秒后，后台生成了一版结果，写入 Result Stream。
前台助手此时并不会生硬地打断用户，而是在一个自然的对话节点把结果接入。

例如，用户刚说完一句别的话后，前台助手顺势接上：

前台助手：
“对了，你刚才说下午如果有空想出去放松一下，我这边已经帮你想了一版。你看看这个路线合不合适：”

“第一站可以先去附近找个环境不错、价格也比较合适的店坐一会儿，吃点东西，顺便把工作状态切换一下。
然后如果你还有精神，可以去一个离得不远的公园或者步道慢慢走一圈，不用太累，但也能稍微活动一下。
整体花费我帮你控制在比较轻松的范围内，路程也不会太折腾。”

“如果你愿意，我还可以继续把它细化成：
吃饭地点推荐 + 过去要多久 + 大概花费 + 回程时间安排。”

说明

这一轮体现的是后台结果的自然拼接式注入：
	•	结果不是机械弹出
	•	不是“任务已完成，以下是结果”
	•	而是由前台以自然对话方式接回来

这样用户感受到的是：

助手一直在和我聊天，同时也真的在帮我做事。
等它想好了，就顺势把结果带回来。

这正是该架构最重要的体验价值之一。

⸻

4. 该场景中的系统内部时序

下面用更工程化的方式说明这个案例背后的协作过程。

⸻

阶段 A：纯前台对话

用户打招呼
→ 前台本地小模型即时风格化回应

特点：
	•	不调用云端重任务
	•	低延迟
	•	建立陪伴感与在线感

⸻

阶段 B：轻查询处理

用户问天气
→ 前台立即承接
→ 快速查询天气
→ 前台补回结果

特点：
	•	前台先说话，避免首 token 沉默
	•	轻任务可快速完成
	•	用户几乎无等待焦虑

⸻

阶段 C：重任务触发

用户提出“下午去哪玩”的需求
→ 前台先承接并继续聊天
→ 中台识别为重任务
→ 生成任务快照
→ 后台 Worker 开始搜索与规划

特点：
	•	用户感知不到系统“切模式”
	•	后台任务与前台对话并行

⸻

阶段 D：对话中补充约束

用户继续说：
	•	不想太累
	•	不要太远

前台记录并更新会话草稿
→ 中台判断是否修补现有任务
→ 后台按新约束调整结果

特点：
	•	任务不是一次性定死
	•	用户可以边聊边修正目标
	•	系统具有连续协作感

⸻

阶段 E：后台结果注入

后台生成结果
→ Result Stream 写入可发布内容
→ 前台选择自然时机接入
→ 以对话式方式反馈给用户

特点：
	•	结果不是突兀插入
	•	而是被前台融入当前对话流
	•	保持自然、连贯、像真人协作

⸻

5. 该案例体现出的核心设计价值

价值 1：实时交互感

助手始终“接得住话”，不会因为后台思考而沉默数秒。

价值 2：前后台解耦

前台负责陪伴和承接，后台负责真正做事，两者互不阻塞。
